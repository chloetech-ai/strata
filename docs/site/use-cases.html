Use cases

Six things one engine does

Search inside an app

A notes app, a store, a help center: the rows already live in a local database, and the search box needs typos, facets and "did you mean" without a second service.

Replaces
SQLite with FTS5, or a database plus an Elasticsearch sidecar
Uses
text columns vectors BM25, typos, synonyms, autocomplete, facets, hybrid
Starts as
One file opened from Python, Rust or the shell
Grows to
A server when a second process needs it, shards when one machine is not enough
SELECT id, title, price, score() FROM products
WHERE MATCH(title, :q, synonyms => 1) AND in_stock
ORDER BY rrf(bm25(title, :q), similarity(emb, :v)) DESC LIMIT 10;

SELECT brand, COUNT(*) FROM products WHERE MATCH(title, :q)
GROUP BY brand ORDER BY 2 DESC LIMIT 8;

Recommendations

"Next for you", "bought together" and "more like this", ranked from the customer's own history at the moment they ask, with every ranking logged and comparable by interleaving.

Replaces
A vector database, a feature store and nightly batch jobs
Uses
vectors graph encode() over a sequence model, personalised PageRank, MAX k PER, the rank log, interleaving
Measured
MovieLens 1M, Recall@10: 0.306 with encode, 0.242 with ppr (CI gate, earlier run). Amazon sets: pending the benchmark.
SELECT id, title FROM products WHERE in_stock
ORDER BY rrf(
  similarity(emb, encode('next',
    (SELECT item, ts FROM reviews WHERE usr = :u ORDER BY ts DESC LIMIT 200))),
  ppr(bought_with,
    (SELECT item FROM reviews WHERE usr = :u ORDER BY ts DESC LIMIT 20))
) DESC MAX 2 PER brand LIMIT 10;

Retrieval for assistants

Find the passages an assistant should read: words for names and codes, vectors for meaning, a reranker for the last hundred rows, and filters for who may see what. Engram, Claude Code's memory, is built this way.

Replaces
A vector database, a keyword index and a reranking service
Uses
text vectors embedded fields (local or hosted models), hybrid fusion, cross-encoders, multi-vector maxsim
Starts as
A file beside the app; the model runs in-process
WITH top AS (
  SELECT * FROM passages WHERE team = :team
  ORDER BY rrf(bm25(body, :q), similarity(emb, :v)) DESC LIMIT 100
)
SELECT id, doc, body FROM top
ORDER BY cross_encoder('bge-reranker-base', body, :q) DESC LIMIT 8;

Photos, sound and video

A file is a column. The database captions images, transcribes recordings and embeds both, so words find a picture and a picture finds its neighbours, one result per video.

Replaces
An object store's index, a captioning job and a vector database
Uses
vectors text MEDIA fields, SigLIP and CLAP embeddings, derived captions and transcripts, DISTINCT ON
CREATE TABLE shots (
  id KEYWORD PRIMARY KEY, item KEYWORD REFERENCES products,
  image MEDIA OPTIONS(kind = 'image'),
  caption TEXT OPTIONS(derive = 'image', model = 'blip-image-captioning-base'),
  emb VECTOR OPTIONS(embed = 'image', model = 'siglip-base-patch16-224')
);

-- :v = {"embed": "a racing game at night", "field": "emb"}
SELECT DISTINCT ON (item) item, id, image FROM shots
ORDER BY rrf(bm25(caption, :q), similarity(emb, :v)) DESC LIMIT 12;

Logs and queries

Strata keeps its own logs and every query it answers in a Strata database, so finding why a shard was slow is a search with SQL, across every server of the cluster.

Replaces
A log shipper and a log search cluster, for the database's own logs
Uses
text columns MATCH over messages, GROUP BY over levels, nodes and minutes, joins of logs to queries
SELECT ts, node, level, message FROM logs
WHERE level IN ('warn', 'error') AND MATCH(message, 'replica OR shard')
  AND ts > '2026-10-31T06:00:00Z'
ORDER BY ts DESC LIMIT 100;

SELECT fingerprint, COUNT(*) AS n, SUM(ms), MAX(ms) FROM queries
WHERE shard = false GROUP BY fingerprint ORDER BY 3 DESC LIMIT 20;

Knowledge graphs

Edges are rows of a table, so a graph is written in the same transaction as the documents it links, and a walk can start from a search.

Replaces
A graph database beside the search index
Uses
graph vectors edge tables, REACHABLE, PATH, hops(), ppr
-- the papers two citations from the closest matches
SELECT id, title, hops() FROM papers
WHERE REACHABLE(cites,
  (SELECT id FROM papers ORDER BY similarity(emb, :q) DESC LIMIT 3),
  hops => 2, dir => 'both')
ORDER BY hops(), id LIMIT 20;

-- one shortest path through surveys
SELECT id, title FROM papers
WHERE PATH(cites, 'p1', 'p9', max_hops => 6, through => kind = 'survey') ORDER BY hops();
