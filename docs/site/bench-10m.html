Cluster · 10M passages · DigitalOcean · 3 and 4 November 2026

Ten times the data, the same budget

The 1M run with ten times the data. Every engine had its own DigitalOcean machines with 6.8 CPUs and 52 GiB, and nine of the fourteen finished.

Strata is fastest on 11 of the 45 tests, more than any other engine, and in the top half on 34. It also has the two worst results of the run: a SQL aggregate (4.3 s) and typo search (824 ms). On latest main, head to head on the same machines, it stays first against Elasticsearch and OpenSearch (below).

Head to head with Elasticsearch and OpenSearch

Strata on latest main (image 055f6bf, with #242 and #245), Elasticsearch and OpenSearch took turns on the same two 4-vCPU machines, three passes each. Strata ran first and again last, 3.4% apart at the median. Of the three, it is fastest on 31 of the 45 tests. OpenSearch serves 1.9 times its BM25 queries a second at 16 clients, and both are faster on typos and SQL aggregates.

Raw data: README.md and the directory. The rest of this page is the full run of 3 November, on the older build.

The 128 GB machine

Milvus and Redis, with more memory

Both needed more than 52 GiB, so they ran with the same CPUs on 128 GB and are not ranked. Redis is fastest on vectors (at recall 0.684) and key lookups, and takes 0.8 to 1.5 s on text. Milvus has the best filtered recall, at about an eighth of Strata's vector throughput. While searching, Redis held 72 GiB, Milvus 64 and Strata 2.2.

Writes and streams

Searchable in 8 ms

Strata and Vespa make a write searchable when it returns (8.2 and 10.0 ms); Elasticsearch and OpenSearch refresh every second. Updates are about twice as fast, because Strata sets one column in place. A crashed stream consumer resumes exactly, since offsets commit with the rows. Solr has no write numbers.

Load and size

Shown, not ranked

Strata's shards were built offline from local files, the others over HTTP, so load times do not compare.

Where Strata is behind

Aggregates, typos, key lookups and recall

  • SQL aggregates. 4.3 s, up from 178 ms at 1M; Elasticsearch and OpenSearch take under 8 ms, likely from their request cache, which the run left on for SQL (our audit). 2.9 s on latest main. In review: #252 reads the groups from the columns, 722 to 27 ms for this query on 5M rows in a container; not yet run on a cluster.
  • Typo search. 824 ms on this build. 81 ms on latest main with #242, still about twice Elasticsearch's 38 and OpenSearch's 45.
  • Key lookups. 0.86 ms, about twice Postgres, Weaviate, ParadeDB and Qdrant.
  • Vector recall. 0.795 at the shared settings, against Qdrant's 0.941 and Postgres's 0.826.
  • BM25 at 16 clients. 493 queries a second against OpenSearch's 777 and Elasticsearch's 608, without the statistics cache (#245). With it on latest main, 470 against OpenSearch's 896 on the same machines: at 10M the shards are what waits (p90 76 ms, median 19). In review: #258 starts each segment at the scores the earlier ones found, 46% more queries a second on one thread in a container.
What did not finish

Five engines that did not run at 52 GiB

  • Typesense ran out of memory at 7.2M documents.
  • Milvus ran out of memory building its index, and ran again on 128 GB.
  • Meilisearch had indexed about 4M documents after nine hours.
  • Manticore was still merging after eight hours.
  • Redis keeps everything in memory, so it ran on 128 GB from the start.
  • Postgres finished, but its text search averaged 28 s a query on a 107 GB table; with a 20 s limit, its text kinds count as not answered.

Strata's first attempt hit a 5 s server deadline on cold vector queries and was run again with the client's 30 s (#244). No number here comes from a failed attempt.
