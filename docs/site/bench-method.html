How we test

How we test, and how we checked ourselves

A benchmark by a database's own authors deserves suspicion. So every engine's request is written down, every raw result is committed, and we audited our own runs before publishing.

The workload

Fourteen kinds of query, the mix an app sends

Each engine runs each kind with its closest native request. Where it has none, the kind counts as not run.

The rules

The same resources, data and settings for all

Equal budgets, enforced

Kubernetes limits: 6.8 CPUs per engine in the cloud, 3 CPUs and 6 GiB on the laptop. Each engine is told its budget.

The same text analysis

Folding, English stopwords, Snowball stemming, BM25 k1 1.2 and b 0.75 everywhere. The Lucene engines' top 10s share 93 to 96% of ChloeDB's.

The same vector settings

HNSW m 16, ef_construction 200, 64 candidates, 8-bit codes re-scored where supported.

No result caches

Result caches off for every engine, its SQL endpoint included, since 5 November (our audit); filter and page caches stay on, and each run records its cache hits. Every answer is recorded and checked.

Pinned versions

Images pinned by tag, ChloeDB by commit, data by SHA-256.

Defaults plus documented tuning

What each engine's own docs recommend, committed beside the results.

What is measured

Latency, throughput and the answers themselves

  • Latency: median and 99th percentile at one client, measured at the client.
  • Throughput: queries a second at 4 and 16 clients, 6 s per cell over 300 queries, after warm-up.
  • Passes: the median of three at 1M (the cold first pass alone would favour ChloeDB). One pass in the 10M run after a longer warm-up, where a second ChloeDB landed within 4.5%; three in its head-to-head on latest main.
  • Quality: recall@10 against exact vector search, and nDCG@10 where the collection has judgments.
  • Writes: inserts and updates at 16 clients, and time until a write is searchable.
  • Streams: a Redpanda topic at rising rates, then a consumer crash; duplicates and losses counted.
The ranking

Summed places, and other rules

Latencies differ a thousandfold between kinds, so averaging speeds would let the slowest kind decide. Places weigh every test the same: 14 kinds × 3 tests (median, 99th percentile, throughput at 4 clients) plus three recall tests, 45 in all. A kind an engine cannot run counts as last. Load is left out, since ChloeDB's shards were built offline.

What changes the order

ChloeDB stays first at 16 clients and with gaps under 15% as ties. At 1M on latest main it is also first on only the kinds every engine runs and on average place; in the first 1M run Milvus led on both, and at 10M, on the older build, Postgres does.

Where to check it

Each report shows all five rules, generated from raw results by the site's data script. Each run's rank.md also ranks load.

Run it yourself

Every run is a script in the repository

A laptop cluster (kind), one engine at a time
cd chloedb-server
deploy/kind-test.sh up
deploy/compare/compare.sh image
deploy/compare/compare.sh up es
deploy/compare/compare.sh load es
deploy/compare/compare.sh run es
deploy/compare/compare.sh down es
Every engine on DigitalOcean, at once
cd chloedb-server
IMAGE=ghcr.io/chloetech-ai/chloedb-server:<sha> \
  BUDGET=30 deploy/compare/fanout.sh run
deploy/compare/fanout.sh analyze results/
deploy/compare/fanout.sh down
No server, on one DigitalOcean node
cd chloedb-py/bench/laptop
./do_part_a.sh up && ./do_part_a.sh push
./do_part_a.sh setup && ./do_part_a.sh prep
./do_part_a.sh run
./do_part_a.sh fetch results/ && ./do_part_a.sh down
These pages' numbers
python3 docs/site/scripts/bench_data.py

Full steps and costs: deploy/compare/README.md. Think an engine is set up badly? Open an issue with the setting you would use and we will run it again.
