Small to big

Start with a file. Add machines when you need them.

Strata does not change shape as it grows. A shard is a Strata file, a server serves one, and a cluster is servers behind a coordinator. Each step adds a process, never a new query language, a new schema or a migration.

1In your program

A file, opened like SQLite

The library links into the app. There is no server to run and no port to open; the app reads and writes shop.strata directly, with every index in it.

  • Python, Rust, or the strata shell
  • Transactions, crash safety and checkpoints in the file
  • Embedding models run in-process
import strata
db = strata.open("shop.strata")
db.query("SELECT id, title FROM products WHERE MATCH(title, :q) LIMIT 10",
         q="racing wheel")
2One server

The same file, served

When a second process needs the data, start a server on the file. It speaks HTTP JSON and gRPC, takes API keys, and serves the command center. The Python client has the embedded database's methods, so the app changes one line.

strata-server --db shop.strata --listen 127.0.0.1:7700
# was: db = strata.open("shop.strata")
db = strata.connect("http://127.0.0.1:7700")
3Replicas

A primary and its copies

The primary ships each transaction to its replicas and answers a write once the copies you ask for hold it. When the primary stops answering, the copies elect a new one.

  • --write-acks all, majority or primary
  • --failover-after-ms for elections
  • Reads that wait for the app’s last write
strata-server --db shop.strata --seq-no \
  --replicas http://b:7701,http://c:7701 --failover-after-ms 3000
4Shards

A coordinator over shards

Rows are placed by slots of their key (or of a column such as the customer). The coordinator plans each query once, sends it to every shard, and merges their answers so that the result matches one database's. Adding a shard moves slots to it while queries and writes go on.

strata-server --shards http://s0:7701,http://s1:7701 \
  --listen 127.0.0.1:7700 --grpc off
5Kubernetes

A cluster the operator keeps

One StrataCluster resource says how many shards, copies and coordinators. The operator makes the pods and volumes, grows and shrinks the cluster by moving slots, replaces a lost copy, and rolls new settings or images through one copy at a time.

cd strata-server/deploy/k8s/operator
kubectl apply -f operator.yaml -f cluster.yaml
kubectl -n strata patch strata demo --type merge \
  -p '{"spec": {"shards": 3}}'
What stays the same

Five steps, one structure

What a developer writes against stage 1 is what runs at stage 5.

The SQL

Every query on the queries page runs at every stage. Over shards, the coordinator's merge gives what one database gives, scores and limits included.

The schema

Tables, field types, embedded models, rank profiles and synonyms are declared once and travel with the data, to every shard and replica.

The file format

A shard is a Strata file. A checkpoint of a cluster's shard opens on a laptop, and a laptop's file can be served as is.

The clients

strata.open and strata.connect have the same methods; HTTP and gRPC are the same on one server and on a coordinator.

The command center

The same pages for one server and a cluster: queries, profiles, relevance, logs, and on a cluster the fleet, slots and rollouts.

Laptop and cloud

The cluster on your laptop is the one in production

On kind the cluster has the same pods, the same operator and the same resource as on EKS or DigitalOcean Kubernetes. What changes is where the image comes from, the storage class and the sizes; the structure, the failover rules and the write acknowledgements do not.

Not yetNo published image yet: a workflow that builds and pushes one is the next pull request of the cluster work. Until then the cloud image is built and pushed by hand.

The command center's Cloud view plans a cluster on EKS or DigitalOcean and estimates its cost; creating one from the page is in review.

cluster.yaml: laptop → cloud
  apiVersion: strata.chloetech.ai/v1alpha1
  kind: StrataCluster
  metadata: {name: shop, namespace: strata}
  spec:
-   image: strata-server:dev
+   image: REGISTRY/strata-server:RELEASE
    shards: 2
    replicas: 3
    coordinators: 1
    storage:
-     size: 1Gi
+     size: 200Gi
+     storageClassName: gp3    # do-block-storage on DigitalOcean
    failoverAfterMs: 3000
    writeAcks: all
    clusterTokenSecret: shop-cluster-token
    resources:
-     requests: {cpu: 500m, memory: 1Gi}
+     requests: {cpu: "4", memory: 16Gi}
The developer loop

From a clone to a three-shard cluster on one laptop

Develop against a file, test against the real cluster topology on kind, and ship the same resource to the cloud. The cluster on the laptop fails over, moves slots and rolls out the way the cloud one does, so those paths get tested before production, not in it.

  • The operator's own tests run the same steps with server processes standing in for pods.
  • A deterministic cluster simulator replays elections, slot moves and lost messages from a seed.
git clone https://github.com/chloetech-ai/strata && cd strata
deploy=strata-server/deploy
$deploy/kind-test.sh up          # a kind cluster in Docker
$deploy/kind-test.sh image       # build the server image, load it
$deploy/kind-test.sh operator    # operator + 2 shards, until Ready
kubectl -n strata port-forward svc/demo 7700   # API and UI
$deploy/kind-test.sh scale 3 3   # a third shard; slots move live
Moving a file to a cluster

The app's file becomes the cluster's data

Export the file's tables and import them through the coordinator, which places every row in its shard's slots. The schema comes with them. Then point the app at the coordinator instead of the file.

strata-server export --db shop.strata shop.sqlite
curl -s -X POST 'localhost:7700/v1/import?format=sqlite' \
  -H 'content-type: application/vnd.sqlite3' --data-binary @shop.sqlite
