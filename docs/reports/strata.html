Strata: full text, structured filters and vectors in one SQL file

An embedded search database in the spirit of SQLite: one file, ACID transactions, SQL. Every table is indexed three ways at once (posting lists, a columnar forward index and vector ANN indexes), and a cost-based planner combines them in a single query. This page is the design, the prototype built from the earlier posting-list research, and its evaluation against SQLite and Tantivy on four BEIR collections.

What it does

One file, one SQL statement, three kinds of index: the planner decides per segment which index drives the query and how the others constrain it.

SQLite answers full-text queries with FTS5 and structured ones with B-trees, but it has no vector index, and its FTS5 scores every match without pruning. Search libraries such as Tantivy rank text quickly but have no SQL, no vectors and no transactions. Vector databases do the opposite. Strata keeps SQLite's packaging (an embedded library, one file, a write-ahead log, snapshot isolation) and puts a search engine inside it.

-- full text, ranked, with structured filters
SELECT id, title, score() FROM docs
WHERE MATCH(body, 'vaccine AND (mrna OR "messenger rna") -animal')
  AND year BETWEEN 2019 AND 2021 AND category IN ('c01', 'c02')
ORDER BY bm25(body, 'mrna vaccine efficacy') DESC LIMIT 10;

-- filtered vector search
SELECT id FROM docs WHERE rating >= 4 ORDER BY similarity(emb, :q) DESC LIMIT 10;

-- hybrid ranking: rank fusion, or a weighted sum of normalised scores
SELECT id FROM docs WHERE year >= 2015
ORDER BY 0.2 * bm25(body, :text) + 0.8 * similarity(emb, :q) DESC LIMIT 10;

-- facets over any result
SELECT category, COUNT(*) FROM docs WHERE MATCH(body, 'vaccine')
GROUP BY category ORDER BY 2 DESC LIMIT 5;

The dialect is plain SQL parsed by sqlparser. Search functions are MATCH (boolean full text with phrases, prefixes and negation, juxtaposition meaning AND as in FTS5), bm25, similarity and distance, and rrf, with named options such as nprobe => 32 or strategy => 'prefilter'. Text fields can be generated from other fields, like SQLite's GENERATED ALWAYS AS, so the searchable body (title and text) is indexed without being stored twice.

Architecture

Strata is layered like SQLite, with a search engine where SQLite keeps its B-tree module. SQL text is parsed and bound to the table's schema, giving a predicate tree (text matches, ranges, IN lists under AND, OR and NOT) and a score expression (BM25, similarity, fusion or a column). The planner decides per segment, from statistics the indexes answer without scanning, how each part is evaluated. Operators run on zero-copy views of the segment's sections, mapped straight from the file.

Storage

SQLite updates B-tree pages in place. Compressed posting lists, bit-packed columns and ANN graphs do not survive in-place updates: the best encodings, such as partitioned Elias-Fano, are chosen per list, and changing one docID means re-encoding the list. SQLite's own FTS5, Lucene and Tantivy all keep their indexes as immutable segments merged in the background. Strata does the same for the whole table and adds SQLite's transactional envelope.

Commit and recovery

The commit protocol is shadow paging, as in LMDB: nothing reachable from a valid meta slot is ever overwritten, so there is no rollback journal.

\[ \text{commit}_{t+1}:\ \text{write extents} \;\to\; \text{fsync} \;\to\; \text{write slot } (t+1) \bmod 2 \;\to\; \text{fsync}, \qquad \text{recover} = \operatorname*{arg\,max}_{s \in \{A, B\},\ \text{crc}(s)\ \text{ok}} \text{txn}(s). \]

A torn slot fails its checksum and recovery falls back to the other one, which still names a complete version. Freed pages wait until no snapshot needs them, plus one extra commit, so the older slot always stays valid. A crash test kills a writer process with SIGKILL at random moments, over and over; after every restart the database equals some committed prefix of the writes.

Writes, snapshots and merges

  • Write-ahead log. Inserts and deletes append checksummed records to a -wal file, synced at commit. On open, committed transactions are replayed and a torn tail is ignored.
  • Memtable. Committed but unflushed documents are searchable at once. A snapshot builds small in-memory segments from them with the same code as on-disk segments, one per 1,024 documents, so a write rebuilds only the last chunk.
  • Snapshots. A snapshot is a reference-counted manifest version. Readers never wait for the writer, and a held snapshot keeps its pages from reuse.
  • Deletes and updates. Each segment has a primary-key index and a delete set, replaced copy-on-write. An update is a delete plus an insert.
  • Merges. A tiered policy merges segments of similar size. It reads the live documents back (stored fields from the doc store, vectors from their sections, generated columns recomputed) and rebuilds every index, which drops deleted documents and re-optimises encodings for the larger lists. vacuum compacts the file.

Indexes

Every field type maps to the structures that serve it. The posting-list study that preceded this design chose the encodings: Loom for ranked text, Pyramid for filter lists, BP128 for short lists.

Full text

The analyzer splits on non-alphanumeric characters, lowercases, folds accents, drops 33 stopwords and applies the Snowball English stemmer. Ranked queries also drop NLTK's 153 English function words and count each term once. Terms sit in front-coded dictionary blocks of 32. Lists of at least 512 documents keep their docIDs as Loom, with frequencies bit-packed per 128 postings and addressed by posting rank; shorter lists use BP128 blocks. Document lengths are one-byte norms. Ranking is BM25 with collection-wide statistics summed over the snapshot's segments, so a document scores the same in any segment:

\[ \mathrm{BM25}(d, q) = \sum_{t \in q} \ln\Bigl(1 + \frac{N - n_t + 0.5}{n_t + 0.5}\Bigr) \cdot \frac{f_{t,d}\,(k_1 + 1)}{f_{t,d} + k_1\bigl(1 - b + b\,\frac{|d|}{\overline{|d|}}\bigr)}, \qquad k_1 = 1.2,\ b = 0.75. \]

Top-k uses MaxScore by default: terms are sorted by their upper bound \(U_t\), and once the threshold \(\theta\) of the current top-k exceeds the sum of the smaller bounds, those lists stop driving iteration and are only probed. Block-Max WAND is available, but on these collections' queries MaxScore measured 1.9–2.6× faster. A filter either drives scoring, when it is small enough that scoring its members directly is cheaper, or is probed per candidate. The crossover is a fitted constant times the filter size against the query's list lengths.

Structured fields

  • Columns. Integers and floats sit in 128-document blocks, frame-of-reference bit-packed, with min/max zone maps per block and per 4,096-document superblock. Two-decimal floats such as rating are detected and stored as scaled integers (0–499).
  • Keyword postings. Each value has a Pyramid docID list (a sorted array below 64 documents), so equality and IN are unions. Per-candidate probes instead use the code column and a bitset of accepted codes, at 6–9 ns against 9–24 ns for Pyramid probes.
  • Range postings. An equi-depth histogram of 64 buckets stores each bucket as a Pyramid list. A range is the union of the buckets it covers plus the two boundary buckets checked against the column. Counting is exact from the histogram for whole buckets. The histogram is also the planner's selectivity estimator.
  • Facets count either by reading the result's codes, or by count-only Pyramid intersections when the result is large and the values few.
  • Doc store. Rows are kept in LZ4-compressed 16 KiB blocks.

Vectors

Each vector field keeps float32 vectors for exact re-ranking and 8-bit codes for scanning. Codes are per-dimension scalar quantised, and the query is quantised too, so the inner loop is an integer dot product on AVX-512 VNNI:

\[ c_i = \Bigl\lfloor \frac{x_i - \min_i}{\Delta_i} \Bigr\rceil, \qquad \langle q, \hat{x} \rangle = \sum_i q_i (\min_i + \Delta_i c_i) \;\approx\; \alpha \sum_i \tilde{q}_i\, c_i + \beta, \]

with \(\tilde q\) the 8-bit query, \(\alpha, \beta\) per-query constants, and one 1,024-dimension score in 10–15 ns. Three index kinds sit on top. Flat scans codes and re-ranks the best \(r\) in float32. IVF stores each k-means cluster's docIDs contiguously, followed by their codes, so a probe is one sequential read and a filter is an intersection with the cluster's docID list. HNSW keeps fixed-degree adjacency arrays in the segment; filtered HNSW traverses through non-matching nodes but only collects matching ones.

Planner

The planner works per segment from statistics the indexes answer in microseconds: exact list lengths for terms and keyword values, histogram counts for ranges, document counts, and the vector index's calibrated cost model. Conjunctions assume independence and disjunctions use inclusion-exclusion:

\[ \hat s(P_1 \wedge P_2) = \hat s(P_1)\,\hat s(P_2), \qquad \hat s(P_1 \vee P_2) = 1 - (1 - \hat s(P_1))(1 - \hat s(P_2)), \qquad \hat s(\neg P) = 1 - \hat s(P). \]

Materialise or probe

A predicate is either evaluated into a document set before ranking, or checked per candidate of the ranking operator. If that operator tests \(m\) candidates, it materialises when

\[ C_{\text{mat}}(P) < m \cdot c_{\text{probe}}(P), \qquad c_{\text{probe}}(P_1 \wedge \dots \wedge P_k) = \sum_{i=1}^{k} c_i \prod_{j < i} \hat s_j \quad (\hat s_1 \le \hat s_2 \le \dots), \]

so a conjunction is probed most selective leaf first, short-circuiting. Inside a materialised conjunction the same test applies child by child: once the running result is small, each remaining child is probed per survivor instead of materialised.

Filtered vector search

Four strategies compete. Pre-filter scans the filter's members exactly. In-index searches IVF or HNSW with the filter applied inside. Post-filter searches unfiltered with \(k' \approx k/s\) and drops non-members. Flat scans everything. Their costs, from the vector index's model, are roughly

\[ C_{\text{pre}} \approx C_{\text{mat}} + s\,n\,c_{\text{sq8}}, \qquad C_{\text{HNSW}} \approx \frac{\text{ef}\cdot M\,c_{\text{dist}}}{s_{\text{near}}}, \qquad C_{\text{IVF}} \approx \frac{\text{nprobe}}{\sqrt{s_{\text{near}}}}\cdot\frac{n}{n_{\text{list}}}\,c_{\text{sq8}}, \qquad C_{\text{post}} \approx C_{\text{index}}\Bigl(\frac{k}{\min(s, s_{\text{near}})}\Bigr). \]

The index strategies pay for the selectivity near the query, \(s_{\text{near}}\), not the global \(s\). A filter on a topic far from the query has almost no members among the query's neighbours, so HNSW wanders through thousands of nodes. When the global estimate favours an index strategy, the planner measures \(s_{\text{near}}\) with a 32-result unfiltered search and re-plans:

\[ \hat s_{\text{near}} = \frac{\bigl|\{\, d \in \mathrm{NN}_{32}(q) : P(d) \,\}\bigr| + \tfrac12}{32 + 1}. \]

Hybrid ranking

Reciprocal rank fusion and weighted fusion are both one SQL expression:

\[ \mathrm{RRF}(d) = \sum_{i} \frac{1}{60 + \mathrm{rank}_i(d)}, \qquad \mathrm{W}(d) = \sum_i w_i\, \frac{s_i(d) - \min_{C} s_i}{\max_{C} s_i - \min_{C} s_i}, \]

where \(C\) is the union of each input's top 100. With exact => 1, \(C\) is every row passing the filter, which gives the reference ranking for measuring how much the top-100 shortcut loses.

Evaluation

Four BEIR collections, with Cohere embed-english-v3 vectors (1,024 dimensions) for documents and queries, and human relevance judgments: SciFact (5,183 documents), FiQA (57,638), TREC-COVID (171,332) and Quora (522,931). Each document also has synthetic structured fields: year uniform over 1990–2024, category Zipf-distributed over 64 values, rating uniform over [0, 5). A content-correlated topic (the k-means cluster of the document's vector) gives filters that correlate with queries. One generated workload per collection is run by all three systems: BM25, boolean, filter, vector, hybrid and facet queries, at filter selectivities from 0.1% to 50%.

Each system is fully built (one Strata segment, one Tantivy segment after merging, one SQLite file), then measured single-threaded on a 4-core Xeon with AVX-512, nothing else running. Warm latency is the median of up to three repetitions per query. Cold runs close the database, evict its files from the OS page cache, reopen and run one query; pages read are the file pages the query brought into the page cache.

Build time and size

Strata builds every index of the table in one pass: text, structured, doc store, keys, float32 and 8-bit vectors, and an HNSW graph. That takes 0.9 s for SciFact and 242.5 s for Quora, against 0.6–27.2 s for SQLite and 0.7–18.2 s for Tantivy. Neither baseline builds a vector index: SQLite keeps the vectors as blobs and scans them, and Tantivy has none.

The graph is most of the difference. It takes 13.5 s of FiQA's 17.4 s, 43 s of TREC-COVID's 63.6 s and 201 s of Quora's 242.5 s, on four threads. The rest of the load takes 3.9–42 s, 0.9–1.5× SQLite's time. With IVF instead of HNSW, TREC-COVID builds in 36.6 s and Quora in 91.2 s.

The Strata and SQLite files are close in size because both are dominated by float32 vectors, 4 KiB per document. Vectors are 83% of Strata's TREC-COVID file and 97% of Quora's. That share covers the float32 copy kept for re-ranking, 1 KiB of 8-bit codes per document, and 128 bytes of graph. Tantivy, which stores no vectors, takes 7–180 MiB.

Without vectors, Strata's text index is the smallest of the three. With positions, it takes 44.5 MiB on TREC-COVID, against 60.0 MiB for Tantivy and 70.0 MiB for FTS5. On Quora it takes 11.8 MiB, against 21.1 and 25.3 MiB. Part of that gap is the 33 stopwords Strata drops at index time, which the baselines keep. A posting, with its docID and frequency, costs 12.2–12.7 bits. The structured index (columns, keyword postings and range buckets) takes 4.5 MiB on TREC-COVID, against 8.4 MiB for SQLite's four B-tree indexes and 2.7 MiB for Tantivy's columns. The doc store is within 16% of Tantivy's; both use LZ4.

Query latency

Warm, Strata is faster than Tantivy in 23 of the 28 text and filter comparisons:

  • BM25 top-10: 1.8–4.6× faster than Tantivy, and 45–213× faster than FTS5, which scores every match.
  • Two-term conjunctions: 3.6–6.7× faster than Tantivy.
  • Filtered BM25: 3.5–4.6× faster than Tantivy.
  • Vector top-10: 0.09–0.20 ms with HNSW. SQLite's scan takes 12 ms on SciFact and over a second on Quora.
  • Hybrid queries: 0.36–1.3 ms. They run BM25 and the vector index, then fuse their top 100s.

The exceptions are facet counts, where Tantivy is 1.1–2.7× faster, and SciFact's three-term conjunctions. These queries take 12–124 µs in Tantivy. At that size, the fixed cost of a SQL statement shows: a query that matches nothing takes Strata 7–10 µs to parse, bind, plan and run. That is about half of the facet gap on SciFact. The rest is that Strata materialises the match before reading category codes, while Tantivy's collector reads its column inside the intersection.

Cold, every system waits on page faults and the gaps narrow:

  • Text queries: Strata is within 0.7–1.5× of Tantivy. It is faster on TREC-COVID (BM25 in 3.8 ms against 5.0 ms) and 11–27% slower on BM25 for the other three collections.
  • Structured filters: Strata is 1.8–2.9× slower than Tantivy's columns. A range touches histogram buckets, boundary blocks, zone maps and the key index, each on different pages.
  • Vectors against SQLite: a cold vector query is 50–63× faster on the two large collections. HNSW touches about 1,000 pages, where the scan reads all 239,000 or 592,000. On SciFact, a cold scan of SQLite's 20 MiB of vectors is as fast as a cold graph walk (27 against 29 ms).

Cold reads and page-cache hints

Cold latency depends on what the kernel reads around each page fault, and the right policy differs by section. The table compares three policies on the two large collections:

  • Read-ahead everywhere (the kernel's default). A cold HNSW query reads 20,262 pages on TREC-COVID and takes 83 ms: each random hop through the graph pulls in up to 128 KiB around it.
  • No read-ahead (MADV_RANDOM on the whole file). Vector queries drop to about 1,000 pages and 40–44 ms. BM25, facets and filters, which read postings and columns in order, then fault page by page and are 1.9–3.6× slower than with read-ahead.
  • Default hints. Random access is advised only for sections read at random: the doc store, the key index, term dictionaries, float32 vectors, and the graph with its codes. Postings, norms, columns and IVF lists keep read-ahead. Vector and hybrid queries stay at the random-access cost, and BM25 is 0.7–1.1× its read-ahead time.

Structured filters are the exception: under the default hints they are 1.3–2.1× slower than with read-ahead everywhere. These queries sort by rating and break ties by key. With 500 rating values, a permissive filter leaves hundreds of documents tied at the top. Their keys are scattered over the key index, so each one costs a separate fault. Keeping read-ahead on the docID-to-key half of that index would remove the cost. Per-section hints are a first step; the planner knows each query's access pattern and could choose them per query.

Ranking quality

Strata's BM25 is within 0.017 nDCG@10 of both baselines on every collection, and no system is consistently ahead: Strata leads on SciFact, Tantivy on TREC-COVID, FTS5 on FiQA and Quora. The analysers differ. Strata stems with Snowball and drops stopwords, FTS5 uses the Porter stemmer, and Tantivy uses Snowball and keeps stopwords.

HNSW is within 0.005 of the exact scan on three collections. SQLite ran only 300 of Quora's 2,000 vector and hybrid queries, so the Quora row compares different query sets. On the shared 300, HNSW scores 0.867 against 0.880 exact, with recall@10 0.991; four queries that lost a relevant duplicate account for the whole difference. Strata's RRF is within 0.006 of SQLite's RRF over the same two rankings, also on those 300 Quora queries (0.845 against 0.850).

All three systems drop NLTK's 153 English function words from BM25 queries, so the rankings are comparable; bm25(body, :text, stopwords => 0) keeps them. On the same queries, dropping them gains 0.055 nDCG@10 on TREC-COVID, whose queries are full questions, and 0.002 on SciFact and FiQA. It costs Quora 0.055 (0.756 against 0.811): its questions are short, and "how", "why" or "can" carry much of their meaning.

Quora: SQLite's exact vector and RRF columns cover 300 queries, Strata's 2,000. On the same 300, Strata scores 0.867 (HNSW) and 0.845 (RRF).

Weighted fusion beats both of its inputs on three of the four collections. The best BM25 weight is small, 0.1–0.3: the scales differ, and on these collections the embeddings are the stronger ranking. On TREC-COVID it reaches nDCG@10 0.851, against 0.817 for vectors alone, 0.835 for RRF and 0.658 for BM25. On Quora it reaches 0.920 against 0.899 and 0.859. On FiQA, where BM25 is weak (0.268), fusion only matches the vector ranking (0.437), and RRF falls below it (0.382), because RRF gives both rankings equal weight.

The top-100 shortcut is cheap and close to exact. Against weighted ranking computed over every document, it recovers 89–95% of the exact top-10, and its nDCG@10 is within 0.01–0.03. It costs 0.4–1.5 ms per query, where the exact computation costs 1.8 ms on SciFact, 44 ms on FiQA and 211 ms on TREC-COVID.

Posting formats and top-k

The text index stores long lists (at least 512 documents) as Loom, the aligned partitioned Elias-Fano design from the posting-list study, and short lists as BP128 blocks. The table compares that against BP128 for every list, on the same index:

  • Boolean queries are where Loom pays off. AND is 7.6–12× faster (8.9 against 68 µs on FiQA, 24 against 287 µs on TREC-COVID), and OR 1.5–2.3× faster. Loom's cursors skip with sampled pointers instead of decoding whole blocks.
  • Size is 2–4% smaller than BP128, at 11.7–12.7 bits per posting including frequencies.
  • Ranked top-10 is close: MaxScore is within 0.9–1.3× across formats. MaxScore beats Block-Max WAND by 1.9–2.6× on these queries.

Vector indexes

On Quora (522,931 vectors, 1,024 dimensions), HNSW reaches recall@10 0.962 at 0.054 ms and 0.991 at 0.13 ms (ef 64, the default). IVF needs 0.58 ms for 0.936 (nprobe 32) and 1.8 ms for 0.977. The exact scan of 8-bit codes with float32 re-ranking reaches 1.000 in 38 ms.

The quantised dot product costs 12 ns per vector with VNNI (7.6 ns when four rows are scored at once), against 48 ns in float32. Scoring on the codes alone already ranks the exact top-10 correctly in all 100 sampled queries; float32 re-ranking only settles ties. HNSW took 201 s to build with four threads, IVF 54 s.

Cold, access patterns decide. With the kernel's default read-around, one HNSW query reads 32,290 pages (124 ms). Advising the graph and its codes MADV_RANDOM cuts that to 1,193 pages (54 ms), and prefetching each hop's neighbours cuts it to 15 ms. IVF reads its clusters sequentially, so it is fastest with read-ahead: 15 ms, or 8 ms with prefetching.

Filtered vector search and the planner

Filtered vector search is where one fixed strategy cannot win. The chart shows mean latency per strategy at each filter selectivity on the workload's filters:

  • Pre-filtered scan: its cost grows with the number of matching documents.
  • HNSW with the filter inside: cheap for permissive filters, but very expensive for selective ones, and for filters whose matches sit far from the query.
  • Post-filtering: sensitive to both.

The filters include random ones and topic filters drawn near to and far from the query.

Across 300 filtered vector queries per collection, the planner is 2.1× faster than the best fixed strategy on TREC-COVID (251 ms against 523 ms for always pre-filtering) and 5.3× faster on Quora (451 ms against 2,375 ms). Recall@10 stays at 0.992–0.998. Always using the HNSW index would take 6–16 s. Against an oracle that knows the fastest plan per query with recall ≥ 0.9, the planner spends 1.3–1.6× more time in total.

Two refinements made that gap small. The first measures selectivity near the query. Planning on global selectivity alone, 100 TREC-COVID queries took 328 ms against an oracle's 48 ms. A 32-neighbour sample brought that to 61 ms. On Quora, though, it still sent far-topic 10% filters into 60–100 ms graph walks where a 5 ms scan sufficed: 1,076 ms in total. A second, 160-neighbour sample, taken when the first finds at most one match, brought Quora to 451 ms. The second refinement costs post-filtering with the smaller of the global and local selectivity, since its candidate pool is sized from the global one.

For BM25 with filters, and for structured filters alone, geometric-mean regret is 1.07–1.30. Range filters choose between a zone-map scan and histogram bucket postings, and filtered BM25 chooses between driving scoring from the filter and probing it. On IVF, the planner leans on the index and gets recall 0.93; an oracle limited to recall ≥ 0.9 must spend more, which is why the IVF rows show the planner faster than that oracle.

Transactions and storage

A durable single-document commit is one WAL append and one fsync: 0.27 ms at the median, 3,190 commits per second. Batching amortises the sync. With 1,000 documents per transaction, the WAL takes 87,000 documents per second. Without fsync it takes 155,000–269,000; a process crash still loses nothing then, but a power failure may lose recent commits.

  • Read your writes. Committed documents are searchable at once. The first query after a write rebuilds the memtable's last 1,024-document chunk with every index of the evaluation table, which takes 31–39 ms. An unchunked memtable of 10,000 documents takes 411 ms. Later queries reuse the chunk, and taking a snapshot costs 0.1–0.2 µs.
  • Opening a database reads the meta slots, the manifest and each segment's directory. Cold, that takes 3.3 ms for 10 segments, 13 ms for 100 and 123 ms for 994 (8 ms warm). Replaying 10,000 WAL documents takes 63 ms at open, plus 369 ms to index them at the first query.
  • Merges. A tiered merge of eight 5,000-document segments, 10% of them deleted, rebuilds every index in 2.2 s, about 16,000 documents per second. After a delete-heavy workload the file is 1.22× its compacted size until vacuum.
  • Recovery. The crash test kills a writer process with SIGKILL at a random moment during inserts, deletes, commits and flushes, then reopens. Every restart recovered a committed prefix: 20 runs by default, and 60 and 80 in longer runs. A damaged meta slot falls back to the other one.

Verdict

The design holds up. One file, with ACID commits and a SQL front end, serves full text, structured filters, vectors and their combinations. Warm, it is faster than both specialised baselines on most of the workload, and its quality matches theirs. It pays for that in build time and in cold structured filters.

One embedded file for three index families

Met: every query of the workload, and the ten compound statements, runs as SQL against one file. Commits are durable at 0.27 ms. Every crash test recovered a committed prefix. Snapshots cost 0.1–0.2 µs, and the file is near SQLite's size.

Missed: SQL covers single-table SELECT only; writes go through the Rust API. Building the HNSW graph makes loads 1.5–9× slower than SQLite's (0.9–1.5× without it).

Faster than the specialised engines

Met: warm BM25 is 1.8–4.6× faster than Tantivy, and conjunctions 3.6–6.7× faster. Strata wins 23 of 28 warm text and filter comparisons. Vector queries take 0.09–0.20 ms, against SQLite's 12 ms to 1 s scans, and are 50–63× faster cold.

Missed: Tantivy counts facets 1.1–2.7× faster. Cold structured filters are 1.8–2.9× slower than Tantivy's, because a range touches several sections and key tie-breaks fault one page per key.

Hybrid ranking as one plan

Met: RRF and weighted fusion are single SQL expressions, under the same filter as their inputs. RRF quality equals SQLite's RRF. Weighted fusion adds 0.02–0.03 nDCG@10 over vectors alone on three collections, at 0.4–1.5 ms.

Missed: the top-100 shortcut recovers 89–95% of the exact fused top-10. The best weight differs by collection (0.1–0.3), and nothing picks it automatically.

A planner that adapts per query

Met: for filtered vector search, the planner is 1.5–5.3× faster than the best fixed strategy on the three larger collections, with recall@10 0.992–0.998. For filtered BM25 and filters alone, geometric-mean regret is 1.07–1.30.

Missed: it spends 1.3–1.6× an oracle's time. On SciFact, always pre-filtering takes 19% less time. With 5,183 documents, scanning a filter's members is never expensive, and planning, probing and the occasional index plan add 6–49 µs per query.

Where it fits

  • Embedded retrieval. Applications that want local search over documents with metadata and embeddings, such as retrieval for a model on a laptop, a desktop app's search box, or an edge device. They get SQL and one file to copy, back up or ship.
  • Read-mostly corpora with steady writes. Commits are cheap and visible at once, but merges rebuild every index of the segments they combine, and HNSW builds dominate load time. For write-heavy vector workloads, IVF builds 1.7–2.7× faster.
  • Not for relational workloads with joins, high write concurrency, or corpora larger than one machine.

Limitations

  • One machine. A 4-core cloud VM with an Emerald Rapids Xeon. Small timings vary by about 10–15% between runs. Cold numbers come from evicting the page cache on a virtual disk; a local NVMe drive or a spinning disk would shift them.
  • Synthetic structured fields. year, category and rating are random, so they are independent of the text, which the planner assumes. topic is the k-means cluster of the same embeddings, so it correlates with vector queries by construction.
  • Baselines. SQLite has no vector index here, so its vector numbers measure a scan, not a competing ANN index. Tantivy has no vectors. A fuller comparison would add sqlite-vec and a dedicated vector store.
  • One segment. All three systems are measured after a full merge. Queries over many segments are supported and tested, but not timed here.
  • Single-threaded queries, by design for the comparison. Segments could be searched in parallel.

Next steps

  • I/O planning. Let the planner choose page-cache hints per query from its access pattern, and keep read-ahead on the docID-to-key half of the key index. That would close the cold filter gap.
  • Correlation-aware estimates. Sample multi-predicate conjunctions the way the vector planner samples near the query, instead of assuming independence.
  • Fusion without tuning. Fit the weighted-fusion weight per collection from score distributions, or learn it from clicks. Keep function words in queries that are short, where dropping them costs Quora 0.055 nDCG@10.
  • Writes in SQL. INSERT, DELETE and UPDATE over the existing transaction API. Then incremental HNSW merges, so that merges stop rebuilding the graph.
