What a memory record should be: keys, values and queries for Engram

Engram keeps a coding agent's running context in a Strata table and puts parts of it back into the prompt. Each stored record has a lexical key, a dense key, a value that gets injected, and attributes that queries filter on. This page compares ways to cut and key that context, on two long-conversation benchmarks, on the 26-hour session that built this repository, and by the answers a model gives from what is injected. It also covers where a prompt's time goes and what made it shorter. It ends with Claude Code itself, with and without Engram, on work that depends on earlier sessions. A first test found almost no difference; with the knowledge records added in response, Engram solved all 100 held-out runs against 60 without it. The structure that won is now Engram's.

A record, precisely

Retrieval for an agent's memory has three parts that are easy to conflate:

  • the key: what a query is matched against;
  • the value: what is put into the context when the key matches;
  • the attributes: what structured queries filter and sort on.

They need not coincide. A small key matches precisely but may not carry enough to answer. A context sentence added to a key helps a terse record be found, but can pull it ahead of the record that really holds the answer. A large value carries everything, but a fixed budget then holds only a few of them.

For a turn \(t\) cut into windows \(w_{t,1}, w_{t,2}, \dots\), record \(r_{t,k}\) has

\[ K_{\text{lex}}(r_{t,k}) = w_{t,k} \oplus \mathrm{req}(t)_{:200}, \qquad K_{\text{vec}}(r_{t,k}) = \phi(w_{t,k}), \qquad V(r_{t,k}) = w_{t,k}, \]

where \(\mathrm{req}(t)\) is the user request the turn answers and \(\phi\) the embedder. A prompt \(q\) becomes three queries over the same rows: its analysed terms for BM25 over \(K_{\text{lex}}\), its vector \(\phi(q)\) for approximate nearest neighbours over \(K_{\text{vec}}\), and a predicate \(P\) over the attributes that both searches apply. Engram's default predicate excludes what is still in the context window, \(P = \lnot(\text{session} = s \wedge \text{seq} \ge w_s)\). The two lists are fused, weighted by priors, and packed:

\[ S(r) = \bigl(w\,\widehat{\mathrm{bm25}}(q, K_{\text{lex}}(r)) + (1-w)\,\widehat{\cos}(\phi(q), K_{\text{vec}}(r))\bigr)\bigl(1 + \lambda_\iota\,\iota(r)\bigr) + \lambda_t\,e^{-\Delta\mathrm{seq}(r)/\tau}, \] \[ \text{pack: take records in order of } S \text{ while } \sum_{r \in P_B} \bigl(|V(r)| + h\bigr) \le B, \text{ at most } c \text{ per turn}, \]

with \(\widehat{\cdot}\) min-max normalised over the candidates, \(w = 0.5\), header cost \(h = 80\) characters and budget \(B\).

What was compared

A layout decides the keys: how a turn is cut into rows (whole turns up to 1,500 bytes, or windows of 800, 400 or 200 bytes on line, sentence or word boundaries), what context joins the lexical key (nothing, the request a response answers, or both sides of the exchange), and whether the vector embeds that context too. A presentation decides the value: the row itself or its best 600 bytes, the row widened inside its turn, the row plus the head of the other side of the exchange, or the whole turn.

Every combination is packed into budgets of 1,000 to 8,000 characters and scored on what reaches the model:

\[ \mathrm{AIC}@B = \Pr\bigl[\,a \sqsubseteq \mathrm{norm}(P_B)\,\bigr], \] \[ \mathrm{EIC}@B = \Pr\bigl[\,\exists\, e \in E : |P_B \cap e| \ge \min(80, |e|/2)\,\bigr], \] \[ \mathrm{All}@B = \Pr\bigl[\,\forall\, s \in S_E\ \exists\, e \in E_s : e \text{ shown}\,\bigr]. \]

AIC, the answer in context, asks whether the normalised answer string appears in the packed text. It only applies to questions whose answer appears word for word in an evidence turn and has at least four characters. EIC asks whether an evidence turn \(e \in E\) is shown. All asks whether every evidence session is shown, which matters for questions that aggregate over sessions. The data:

  • LongMemEval-S: 500 histories of about 115,000 tokens, one store each; 470 answerable questions, 147 with a verbatim answer.
  • LoCoMo: 10 conversations of about 600 short turns between two people; 1,536 questions.
  • This repository's session: 26 hours of Claude Code, replayed through Engram's capture into about 1,800 records. 67 probe questions are asked as if in a new session, and 32 after the second compaction (only about what the model no longer had). The answer counts when its regular expression matches the packed text.

Embeddings are static (Model2Vec potion-retrieval-32M, 512 dimensions), and every store is searched exactly so that the layout is the only variable.

Keys and values

The curves show what each layout puts into the model's context as the budget grows. The default chart is the measure that best predicts a correct answer: whether the answer string itself is in the context. The other tabs show the coding session, and the other metrics.

Coding sessions want small keys

In a new session, a 4,000-character injection held the answer to 72% of the 67 probe questions with Engram's old 1,500-byte records, and to 85% with 400-byte windows. At 2,000 characters the figures are 66% and 75%. After a compaction, asked only about what the model had lost, they are 72% and 84%. A coding record (a test run, a stack trace, a long answer) holds many unrelated facts. A 1,500-byte key averages them into one vector, spreads BM25's term frequencies over them, and its best 600-byte snippet often misses the one line that matters. A 400-byte window is about one thing.

Smaller is not always better: 200-byte windows lead at 1,000 characters (70%) but fall behind at 4,000 (84%), because they cut errors and commands in the middle. 800-byte windows win at 4,000 (88%) and lose at 2,000 (70%).

Chat histories barely notice

On LongMemEval the layouts sit within a few points of each other at 4,000 characters. The answer string reaches the model for 84–85% of questions with Engram's old layout, its new one, and plain turns. The new layout matches the old at 4,000 and is ahead at 1,000 characters: an evidence turn is shown for 72% against 67%. The best ranking comes from the plainest layout, whole turns with no context in either key (R@10 0.923, MRR 0.688).

Context belongs in the lexical key only

Adding the request a turn answers to its key helps when turns are short and elliptical. In LoCoMo, where the median turn is 109 characters, it raises the answer in context from 74% to 83% at 4,000 characters. In LongMemEval, putting the request into the vector as well lowers MRR from 0.664 to 0.603 for 400-byte windows. Every response's vector moves towards its request, and responses then outrank the request, which is where the user said what is asked about. Kept in BM25 only, the context costs nothing there and still finds terse records by the words of their task. That is Engram's choice now.

A session is the wrong unit

One row per session finds the right session easily (R@10 0.985 on LongMemEval, among about 48 sessions). But a session is about 10,000 characters, and its best snippet holds the evidence for only 64% of questions at 4,000 characters, against 91% for turns. Coarse keys are fine for routing, not as values.

Small values cover more evidence

A budget holds about nine 400-byte records or five 600-byte snippets. Questions that aggregate over sessions ("how many …", "in total …") need several pieces of evidence at once. Indexing only the user's turns (short) and showing each with the head of the reply puts every evidence session in the context for 81% of multi-session questions at 4,000 characters, against 61% for the old layout. It loses the questions about what the assistant said, though: the answer in context falls to 74%.

The value: show the row, not more

Widening a row within its turn, or adding the head of the other side of the exchange, puts more evidence turns in front of the model but cuts more answer strings in half. For whole turns, 400-byte spans plus the other side's head raise the evidence shown at 4,000 characters from 91% to 92%. The answer string in context falls from 85% to 76%, and so does accuracy (next section). For 400-byte keys, a 600-byte span helps chat answers on paper (answer in context 88% against 84%) but not the coding probes (84% against 85%). Engram shows the row itself.

Keys a model writes

The strongest memory systems in the literature do not index raw turns alone. A model reads each conversation and writes down facts, which become keys, values, or both (LongMemEval's key expansion, Mem0, Zep). To test that on LongMemEval, a small model read every session of every fifth history (4,559 sessions) once. It wrote self-contained facts with dates, each tied to the turn it came from, for example "The user holds a degree in Business Administration, which they feel has helped in their new role." It wrote 66,864 facts, about 15 per session and 152 characters each, for $8.49: $0.0019 per session of about 10,000 characters.

Three ways to use them, on the 94 answerable questions of those histories:

  • Facts only: facts are the rows and the values.
  • Turns and facts: fact rows next to turn rows in one index.
  • Facts in the key: a turn's facts join its lexical key and its vector, and the turn stays the value.

Facts improve ranking (MRR 0.717 → 0.75–0.76, R@10 0.926 → 0.947 with turns), and they change aggregation the most. Every evidence session reaches the context for 70% of multi-session questions at 1,000 characters with facts, against 21% for turns, and 82% against 57% at 4,000. A fact is short and already says what happened, when and to whom.

Read by a model, facts alone gave the best answers on these 100 questions: 78% correct, against 75% for plain turns, 70% for Engram's old layout and 68% for its new one (facts against the new layout: 13 wins to 3, p = 0.02). On multi-session questions the figures are 60%, 52%, 40% and 40%. Mixing facts with turns (74%) did not beat facts alone. The sample is small, and the facts come from a model with their own errors, but the direction agrees with the published systems.

Does it change the answers?

Coverage is a proxy. The test that matters is what a model answers from the context it is given. A small, fast model answered all 500 LongMemEval questions from each context, with the question's date, listing the relevant facts before answering. A larger model graded every answer with LongMemEval's own grading prompts, by question type. The small model was also tried as a grader. It agreed on 89% of the 5,350 answers but was stricter (60% against 66% correct), and it ranked two of the layouts the other way round. The figures here use the larger grader.

Memory takes the model from 7% (it can only decline) to 71–75%. The evidence sessions alone, in full (an oracle retriever with about 27,000 characters), reach 92%. That leaves 16 to 21 points to retrieval.

  • Layouts: plain turns with no context gave the most correct answers on these chat histories, 75.4% against 70.6% for Engram's old layout (34 against 10 questions, p < 0.001). The new 400-byte layout lands between them at 73.0%, ahead of the old one at 2,000 characters too (62.2% against 59.6%). Neither of those two gaps is significant.
  • Value size: 400-byte spans plus the other side's head cost 6 points against whole turns (p < 0.001), as the answer-in-context measure predicted. Doubling the budget to 8,000 characters gains them back.
  • Grouping: putting the records under one heading per conversation with its date changed nothing (68.2% against 69.4%).

Coverage predicts the answer closely. When the answer string was in the context, 92–94% of answers were right; when it was not, 0–4%.

By type, the gaps to the oracle are in multi-session questions (44–55% against 84%) and temporal reasoning (68–74% against 94%). Both need several pieces of evidence and their dates at once. That is what model-written facts address, and what a time-aware query would (see the design).

Memory or the whole history?

The same model read the whole history of every tenth question: about 170,000 tokens, in order, with dates. It answered 84% of those 50 correctly. With Engram's 4,000-character context (2,750 tokens, 62 times fewer) it answered 72%, and with plain turns 78%. That is $0.17 per question against $0.0007. The oracle answered 94%. Long-context reading wins on accuracy when the history fits and the cost is acceptable. But a project's history outgrows any context window (a million records is about 400 MB of text), and memory still costs about 240 times less per prompt.

In Engram now

Engram now cuts records at 400 bytes (head and tail of long outputs kept in 1,500-byte units as before). It embeds a record's text without its context, packs up to twelve records with at most eight per user turn, and gives the brief tier three records. Run through Engram's own pipeline, with the gate refitted for the new records:

Both benchmarks gain coverage in their own pipeline: the injection holds evidence for 89.4% of LongMemEval questions (88.7% before) and 72.7% of LoCoMo questions (68.3%). The brief tier, three small records instead of two snippets, gains the most: 77% against 69% on LongMemEval and 52% against 43% on LoCoMo. The refitted gate brings evidence to 77% of LongMemEval questions instead of 67%, and 65% of its injections hold evidence instead of 59%, for about 1,000 characters per prompt.

On this repository's 26-hour session, with the gate deciding as it does in Claude Code:

  • New session: the gated injection answered 50 of 67 probes (42 before), the full injection 58 (46), and one search 58 (54).
  • After a compaction: of the 30 probes the model no longer had, the full injection answered 29 (22 before) and the gate 25 (23).

The first version of this change kept the old cap of three records per user turn and lost two lost-detail probes. The answer was the fourth window of a turn already shown. A coding turn spans many records, so the cap is now eight.

Execution time

A prompt's recall is two index searches, and almost nothing else. Stores of 10,000, 100,000 and a million records were built from LongMemEval turns cut the new way, and timed on four cores with the static embedder.

BM25 and the vector search each take about half of the search (4.0 and 4.4 ms of 8.8 ms at a million records; 1.8 ms in all at 10,000). Embedding the prompt, fusing, and packing take a fraction of a millisecond. The gate's IDF lookup used to run one COUNT query per query term (1.1 ms at a million records). It now reads each segment's term dictionary (0.05 ms).

The stall after a write

The largest cost was not in the search at all. A write adds records to the memtable, and the next query rebuilds the in-memory segment of its last chunk. That chunk held up to 1,024 records, and the rebuild built a full HNSW graph over them: 22–25 ms. A query right after a tool call stored its result waited for it. That is a PreToolUse before an edit, or the next prompt in a fast exchange.

Strata now takes separate build options for memtable segments (DbOptions::mem_build), and Engram builds them without a graph: a scan of at most 256 vectors costs less than building one. Chunks hold 256 records. The rebuild fell from 22–25 ms to 1.4–1.5 ms. A query right after a write now costs what any query costs: 4.1 ms instead of 24 at 10,000 records, and 11.5 ms instead of 38 at a million (p99 34 instead of 110). Disk segments keep their HNSW graphs, and a new Strata test checks that flat memtable segments return the exact top ten.

The hook itself

Claude Code runs a command hook as a new process. Starting engram hook, reading the payload and connecting to the socket costs about 3 ms per event, at any store size, on top of the daemon's work. An event Engram ignores takes 3.3–3.5 ms that way, and 0.6 ms from a client that is already running.

The daemon also wrote its whole session state to disk before answering each hook. It now writes it after the response, when the state has changed. That took storing a tool call from 1.6 to 0.7 ms inside the daemon, and the whole hook from 4.5 to 3.4 ms. A prompt's hook went from 17.1 to 14.2 ms at a million records.

What remains is mostly the process. Claude Code can also send hook events over HTTP to a URL for every event except SessionStart, with the same JSON both ways. A daemon listening on localhost would save the 3 ms of process start for every tool call. It needs a secret path and a Host check first, so that no web page can post into memory. That is the next step for time.

Two smaller changes:

  • Daemon start: the embedding table (129 MB) is now memory-mapped instead of read and converted, which took 70–160 ms. The first hook of a session, which starts the daemon, now takes 85–108 ms (second table above) instead of about 300 ms.
  • Storage: 400-byte records double the record count of a session, and so the file. This repository's session, up to where the probes are asked, goes from 1,835 records to 3,849. A million records (3.5 GB, mostly vectors) is now about 200 sessions of that size instead of 450.

With and without Engram

Everything above measures what reaches the model. The direct test is Claude Code itself, with and without Engram, on work that depends on earlier sessions. Each test has two parts:

  • History: headless working sessions on a small Python project, recorded by Engram. Along the way the user states rules, decisions with their reasons, failed approaches, and requirements for work planned later. Some of these end up in the code; others are only said.
  • Follow-up tasks: each runs in a fresh headless session on a clone of the repository as the history left it, with Engram (its store as the history left it) and without it (no hooks, no memory tools). Both conditions have every normal tool, including files, shell and git history. A script grades each result with one check per fact, so a task is solved only when every remembered requirement holds. The same small, fast model runs everything.

The first test: almost no difference

On the first project, Tally (an expense-splitting library), Engram solved 26 of 30 runs and the agent without it 25 (permutation test within tasks, \(p = 0.33\)). The difference was one task, the accountant's CSV export, whose requirements the prompt's recall brought back. The rest of what the history said reached the model only where it was also in the repository.

Replaying the prompts against the store showed why:

  • For "should we move storage to SQLite and use pandas?", search ranked the record holding the decision and its reason first. But that record is one long user message about several things, so its similarity to the question is moderate, and the gate scored the prompt 3.4 against a threshold of 4.5.
  • The briefing at session start carried only sentences picked from prompts by cue words ("always", "never"). Decisions given with a reason, and requirements announced for later, were not among them.
  • The model called the memory tools twice in 30 runs.

What changed

  • Distillation: after each turn, off the prompt's path, a small model reads the request, the commands and the reply. It also sees the latest 40 knowledge records, and writes new ones (decision, rule, planned requirement, fact). An item that updates an older one retags it superseded; planned work the turn completed is retagged done. A new item whose analysed terms overlap an existing one by a Jaccard index \(J \ge 0.6\) is dropped.
  • Briefing: it now leads with planned work, rules, decisions and facts, in that order, followed by where the last session left off. It opens with an instruction to search memory before design decisions, and it fills up to 6,000 characters.
  • Knowledge block: each prompt gets up to four knowledge records not yet shown, whatever the gate decides. A record qualifies on its own text:
\[ \cos\bigl(\phi(q), \phi(r)\bigr) \ge 0.40 \quad\lor\quad \mathrm{cov}(q, r) = \frac{\sum_{t \in q \cap r} \mathrm{idf}(t)}{\sum_{t \in q} \mathrm{idf}(t)} \ge 0.30, \qquad r.\text{kind} \in \{\text{decision}, \text{preference}, \text{fact}, \text{note}, \text{todo}_{\text{planned}}\}. \]

Strata needed no change. The knowledge query is the same hybrid search under a kind IN (…) predicate, which the planner already runs as a scan of the few matching rows. The briefing is a handful of structured queries.

These were developed on Tally. Its store was distilled after the fact (engram distill), and the Engram condition was rerun against the earlier runs without Engram, on the same repository snapshot. It solved 30 of 30, including the SQLite question it had failed every time, against 25 of 30 (\(p = 0.02\)). But Tally can separate the two conditions on only two tasks, and it was used for development, so it cannot be the verdict.

Held out: two new projects

Two new projects were written by a separate agent, which did not see Engram's code or design, before Engram's changes were tested on them:

  • Stock keeping for a hardware wholesaler: 3 sessions, 13 turns.
  • Appointment booking for a physiotherapy practice: 3 sessions, 14 turns.

Each has ten follow-up tasks:

  • Six need something said only in conversation, such as FIFO valuation and why, a planned count sheet in walking order, the client's Python 3.8 machine, a 42-character receipt printer, a cancellation-fee schedule, or an approach tried and abandoned.
  • Two need a convention that is in the repository.
  • Two are controls that need nothing from earlier sessions.

Engram was frozen first, at the commit the histories ran on. The histories were recorded live, with distillation on. The tasks then ran five times per condition, 200 runs in all, and nothing was changed after.

With Engram, every one of the 100 held-out runs was solved; without it, 60. All of the difference is on the tasks that need something said only in conversation: 60 of 60 against 20 of 60. Where the fact was in the repository, and on the controls, both conditions solved all 40, so the 6,000-character briefing did no harm.

Without Engram, the failed checks are exactly the facts that were only said:

  • Purchase suggestions did not order up to three times the reorder point (5 of 5 runs), and the count sheet was not in walking order by bin (5 of 5).
  • Every answer recommended tomllib, which needs Python 3.11, without knowing that the client's machine runs 3.8.
  • The day plan overran the 42-character receipt printer (5 of 5), and the cancellation fee was wrong (5 of 5).
  • Online booking did not treat seven treatments a day as fully booked (5 of 5), and no answer knew that a calendar feed had been tried and stopped.

Three of these tasks were solved either way: the history had built the series booking and the SMS text, and the agent chose FIFO valuation on its own.

The permutation test shuffles the condition labels within each task, 20,000 times, so a difference between tasks cannot pass for an effect. With no shuffle reaching the observed difference, \(p\) is below \(1/20{,}001\). Fisher's exact test on the pooled solved counts gives \(p \approx 10^{-14}\). The interval resamples tasks, then runs within each task.

The briefing did most of the work. It reached every Engram run, at its full 6,000 characters. The model called the memory tools in 9 of 100 runs, mostly for the two advice questions. The gate held back raw records on 4 of the 20 tasks, and all of those were still solved.

Engram runs took fewer steps: 6.3 against 7.5, and 7.0 against 9.0. They also read 5–6% fewer input tokens, and cost about the same ($0.007–0.009 a run) at the same wall time.

Distillation adds a small model call after every turn of real work. The table below covers the three histories, at about $0.0013 a turn. It never delays a prompt.

The knowledge query adds two filtered searches to every prompt. Run after the main search, they raised the prompt hook at a million records (1% of them knowledge) from 14.2 to 22.0 ms at the median, and from 32.0 to 43.0 ms at p99. They depend on nothing the main search computes, and only packing needs both results, so they now run side by side: 14.7 ms at the median and 29.8 ms at p99, the same as before within noise.

The limits:

  • Three small projects, one history each, and one small model for the work and for distillation.
  • The tasks were written alongside the histories, each aimed at facts the history states. Real work rarely depends on earlier sessions this often, so the 40-point gain is a gain on such tasks, not on work in general.
  • The histories are short. A project with more knowledge than 6,000 characters leaves the rest to the knowledge block and to search, which has not been tested here.

The design

Store everything as small records: a 400-byte window of one event is the value, the window plus its turn's request is the lexical key, and the window alone is the dense key. Keep every attribute a query can filter on. Derived records (episode cards, summaries, and model-written facts) are extra keys over the same history.

The queries

Every prompt (automatic)

First the knowledge query: the same two searches under kind IN ('preference','decision','fact','note','todo'), keeping at most 4 records not yet shown with cos ≥ 0.40 or coverage ≥ 0.30, whatever the gate says. Then lexical: bm25(body, :q) top 50, and dense: similarity(emb, :v) top 50, both under NOT (session = :s AND seq >= :w). Fuse, apply priors, gate, then pack at most 12 records, 8 per turn, within 4,000 characters (3 records within 1,200 on weak evidence).

Session start (automatic)

Structured only, newest first in each section: kind = 'todo' AND tag = 'planned', then 'preference', 'decision', 'fact', never superseded or done; the latest checkpoint's task list; the last session's episode cards. Within 6,000 characters, with a line telling the model to search memory before design decisions. After a compaction it also runs the prompt query on the last two prompts.

After each turn (background)

A small model reads the turn and the latest 40 knowledge records and writes new ones (tag = 'distilled' or 'planned'), retagging those it replaces 'superseded' and planned work it saw finished 'done'. Off the prompt's path.

Before an edit (automatic)

Structured and lexical: MATCH(files, :path) AND kind IN ('error','decision',…) ORDER BY seq DESC LIMIT 3, once per file per context window.

The model's own tools

memory_search (hybrid, with kinds), memory_timeline (session = :s AND seq BETWEEN :a AND :b), and memory_sql for any read-only question over the attributes.

-- "what failed in the planner yesterday?" through memory_sql
SELECT id, ts, text FROM memory
WHERE kind = 'error' AND MATCH(files, 'planner') AND ts >= 1791700000
ORDER BY ts DESC LIMIT 5

What to keep

Keep all of it. Raw events (prompts, answers, tool calls and results, the commentary between tool calls, compaction summaries) are the source of truth. Episode cards, summary sections and, next, model-written facts are keys derived from them, and can be rebuilt when the layout changes. Large tool outputs keep their head and tail, and file reads are stubs, since the file is on disk.

One trade-off left

On chat histories, 1,500-byte turns with no context gave the most correct answers (75.4%, against 73.0% for 400-byte windows; not significant). On coding sessions the windows win clearly. Engram is for coding sessions, so the windows stay. Cutting prompts and answers at 1,500 bytes and tool output at 400 is an untested middle path.

Done since: knowledge written by a model

The first item of the earlier list is in Engram now (see With and without Engram): at Stop, in the background, a small model writes decisions, rules, planned work and facts as their own records, with Engram's hooks off for that call. Strata needed no change for it. The knowledge query is a filtered hybrid search on kind, which Strata already plans as a scan of the few matching rows, and the briefing is a set of structured queries.

Next, in order of evidence

  1. Time-aware queries. Temporal questions are the second-largest gap (68–74% against 94% with the oracle). Phrases such as "yesterday", "last week" or "before the refactor" map to a ts or seq range that Strata already filters on.
  2. HTTP hooks. Claude Code can POST hook events to a URL for every event except SessionStart, which stays a command hook and starts the daemon. That removes a process start from each tool call (see Execution time). The daemon would need a secret path and a Host check, so that web pages cannot write into memory through localhost.
  3. A reranker on the top candidates of prompts that pass the gate, which still cannot tell related from relevant well.
  4. A larger briefing budget, or ranking within it. A long project will hold more knowledge than 6,000 characters. Beyond that, the briefing keeps the newest items and the knowledge query has to find the rest by similarity, which has not been tested here.
