Intersecting and merging compressed posting lists

I implemented 13 posting-list representations and 20 intersection and union algorithms in Rust, built a testbed that checks every query result before it is timed, and ran them on synthetic and real collections. This page explains each technique with its formulas and layout, then reports what was measured.

The problem

An inverted index maps every term \(t\) to its posting list \(\mathcal{L}_t\): the strictly increasing docIDs of the documents that contain it, drawn from a universe of \(u\) documents. A query \(q = \{t_1, \dots, t_k\}\) is answered with set operations over the lists:

\[ \mathrm{AND}(q) = \bigcap_{i=1}^{k} \mathcal{L}_{t_i}, \qquad \mathrm{OR}(q) = \bigcup_{i=1}^{k} \mathcal{L}_{t_i}, \qquad \mathcal{L}_t \subseteq [0, u),\ n_t = |\mathcal{L}_t| . \]

Lists are stored compressed, so the representation decides both the index size and how cheaply a list can be scanned (next) or skipped through (NextGEQ(x), the first posting \(\ge x\)). For two lists with \(m \le n\) postings, any comparison-based intersection must distinguish all interleavings of the two lists, which gives the lower bound

\[ \log_2 \binom{n+m}{m} \;=\; m \log_2 \frac{n}{m} + O(m) \ \text{comparisons}, \]

so when the lists differ a lot in size, a good algorithm touches only a small part of the longer list. Union is different: its output alone has up to \(N = \sum_i n_i\) elements, so the work is dominated by sequential decoding and by how cheaply the results can be merged.

The two figures of merit used throughout are space and query time:

\[ \text{bits/posting} = \frac{\sum_t \lvert \mathrm{enc}(\mathcal{L}_t) \rvert}{\sum_t n_t}, \qquad \text{ms/query} = \min_{r \in \text{reps}} \frac{T_r}{|Q|} . \]

\(\lvert \mathrm{enc}(\cdot) \rvert\) counts payload plus every skip pointer, directory and header needed at query time, which is what a serialized index would occupy. \(T_r\) is the wall-clock time of repetition \(r\) over the whole query log \(Q\).

The testbed

The crate is organised around three traits. Every representation implements PostingList (build, size, decode). Representations that can be iterated with skipping implement CursorList, whose cursor exposes docid(), next() and next_geq(x). Representations with their own multi-list algorithms (Roaring, tries, the hybrid index) also implement SetOps. The harness runs every applicable algorithm on every representation, so each codec is measured both through the generic cursor interface and through its native operations.

Representations

The 13 representations fall into four families. All lists in a query share one universe, and every docID is below \(2^{32}-1\), which the cursors use as the end-of-list sentinel.

Gap coding in blocks: VByte, BP128, OptPFor, interpolative

Block codecs cut a list into blocks of 128 postings. Within a block they code d-gaps, which are small when docIDs are dense, relative to a base \(b\) (the previous block's last docID plus one):

\[ g_0 = d_0 - b, \qquad g_i = d_i - d_{i-1} - 1 \quad (1 \le i < 128). \]

A skip table stores each block's last docID and byte offset, 64 bits per block, the same as PISA's block_posting_list. NextGEQ gallops over the skip table, decodes one block and binary-searches inside it.

VByte
7 data bits per byte with a continuation flag: \(8 \lceil w(g)/7 \rceil\) bits per gap, where \(w(g) = \lfloor \log_2 g \rfloor + 1\) is the bit width. Byte-aligned and branchy.
BP128
Frame of reference: one width \(b = w(\max_i g_i)\) per block, so a block costs \(8 + 128\,b\) bits. Values are packed in SIMD-BP128's vertical 4-lane layout so that unpacking is the same shift and mask on 4 lanes. The code is written lane-wise with a compile-time \(b\), and LLVM vectorises it.
OptPFor
Patched frame of reference. Gaps wider than \(b\) bits become exceptions, stored as a position byte plus their high part in VByte, and \(b\) is chosen per block to minimise \[ \mathrm{cost}(b) = 16 + 128\,b + \sum_{g_i \ge 2^b} \Bigl(8 + 8 \Bigl\lceil \tfrac{w(g_i) - b}{7} \Bigr\rceil\Bigr) \ \text{bits}. \]
Interpolative
Binary interpolative coding (Moffat & Stuiver). The middle element \(d_m\) of a range \([\ell, r]\) holding \(n\) values is coded in the range it can actually occupy, then both halves recurse: \[ d_m \in [\,\ell + m,\ r - (n - 1 - m)\,] \;\Rightarrow\; \lceil \log_2 (r - \ell - n + 2) \rceil \ \text{bits}. \] A run of consecutive docIDs costs zero bits.

Elias-Fano and partitioned Elias-Fano

Elias-Fano splits each value into \(\ell\) low bits, stored verbatim, and a high part, stored in unary in a bitvector. Element \(i\) with high part \(h_i\) sets bit \(h_i + i\):

\[ \ell = \Bigl\lfloor \log_2 \frac{u}{n} \Bigr\rfloor, \qquad \text{bits} = \underbrace{n\,\ell}_{\text{low}} + \underbrace{n + \lfloor u / 2^{\ell} \rfloor + 1}_{\text{high}} \;\le\; n \Bigl( 2 + \Bigl\lceil \log_2 \frac{u}{n} \Bigr\rceil \Bigr). \]

Bucket \(h\) of the high bits starts right after the \(h\)-th zero, so NextGEQ(x) jumps to \(\mathrm{select}_0(\lfloor x / 2^{\ell} \rfloor - 1) + 1\) without decoding anything before it. The implementation samples every 256th zero to answer \(\mathrm{select}_0\) in constant time, and scans instead when the target is within a few buckets, as PISA does.

Plain Elias-Fano ignores clustering: its size depends only on \(u\) and \(n\). Partitioned Elias-Fano (Ottaviano & Venturini) cuts the list into partitions and codes each one relative to its own base with the cheapest of three encodings: a full run (no payload), a bitvector over the partition's range, or Elias-Fano over that range. The partitions are chosen by dynamic programming over boundaries every 32 postings:

\[ C(j) = \min_{\substack{i < j \\ j - i \le 4096}} \Bigl[\, C(i) + 64 + \min\bigl\{ \mathrm{EF}(i, j),\ \underbrace{d_{j-1} - d_{i-1}}_{\text{bitvector}},\ \underbrace{0}_{\text{if a run}} \bigr\} \Bigr], \]

where 64 bits pays for the partition's entry in the upper level (last docID and descriptor), the fixed cost PISA uses.

Roaring bitmaps

Roaring partitions the universe rather than the list. The high 16 bits of a docID select a chunk; the low 16 bits go into that chunk's container, whichever of three is smallest:

\[ \text{array: } 16\,c \ \text{bits}, \qquad \text{bitmap: } 2^{16} \ \text{bits}, \qquad \text{run: } 16 + 32\,r \ \text{bits}, \]

for \(c\) values in \(r\) runs; arrays switch to bitmaps at \(c = 4096\), where \(16c = 2^{16}\). Because every list uses the same chunk boundaries, AND and OR proceed chunk by chunk with container-pair kernels and need no NextGEQ per element:

  • array ∩ array: SSE4.2 pcmpistrm all-pairs compare (CRoaring's intersect_vector16; on NEON, an 8×8 compare against ext rotations with tbl compaction), or galloping when one side is more than 64× larger;
  • bitmap ∩ bitmap: word AND with popcount;
  • array ∩ bitmap: bit probes;
  • union: a k-way merge over keys that ORs dense chunks into one bitmap and counts it once at the end.

Compact binary tries

Arroyuelo & Castillo (CPM 2023) store a set as the binary trie of height \(h = \lceil \log_2 u \rceil\) that spells every docID most significant bit first. Each node contributes two bits, "left child present" and "right child present", and the bits of a level form a bitvector \(B_\ell\) with rank support. Children are found by counting ones:

\[ \mathrm{left}(i) = \mathrm{rank}_1(B_\ell, 2i), \qquad \mathrm{right}(i) = \mathrm{rank}_1(B_\ell, 2i + 1). \]

Intersection walks all \(k\) tries in lockstep and ANDs the 2-bit codes at each node, so a subtree missing from any input is pruned immediately. This runs in \(O(k\,\delta \log(u/\delta))\) time, where \(\delta\) is the alternation: the size of the smallest certificate that proves the result. DocIDs that are close share their upper paths, so clustered lists need few nodes. The run-compressed variant (Run-Trie) cuts every full subtree and codes its root as 00.

Hybrid bitmap + list index

Culpepper & Moffat's hybrid stores a list as a plain bitmap of \(u\) bits when it is dense, \(u / n \le 8\) (at most 8 bits per posting), and as BP128 otherwise. Conjunctions intersect only the sparse lists, rarest first, and then filter every candidate with \(O(1)\) bit probes. Lucene 10.2 uses the same idea per block, storing dense blocks as bitsets.

Algorithms

Two sorted arrays

merge
Two pointers, \(m + n\) comparisons. The branch-free variant derives both pointer increments from the comparison result.
binary search
Search each element of the short list in the rest of the long list: \(m \log_2 n\).
galloping
Exponential search from the last position, probing 1, 2, 4, … steps ahead, then a binary search: at most \(2 \sum_i \log_2(g_i + 1) \le 2m \log_2(n/m + 1)\) comparisons, which matches the lower bound up to a constant.
Baeza-Yates
Binary-search the median of the short list in the long list, then recurse on both sides: \(O(m \log(n/m))\) on average.
SIMD block merge
Compare a block of \(W\) values from each list all-against-all with \(W\) vector compares against rotations of one block, compact the matches, and advance the block with the smaller maximum. Kernels for SSE (\(W = 4\)), AVX2 (\(W = 8\)) and AVX-512 (\(W = 16\), which emulates VP2INTERSECT), and for NEON (\(W = 4\), and \(W = 8\) with two 128-bit registers a side; ext rotations and tbl compaction). The timed kernels are the NEON ones.
adaptive
SIMD block merge when \(n/m \le 64\), galloping beyond, which is CRoaring's switch point.

k lists

SvS
Set versus set: sort by length and intersect the two shortest lists, then intersect the running result with each next list. Barbay et al. and Culpepper & Moffat found it the fastest in practice.
Small Adaptive
Demaine, López-Ortiz & Munro: take the next element of the currently shortest list and gallop for it in the others, re-sorting by remaining length.
Sequential
Barbay & Kenyon's round-robin eliminator, optimal for the alternation measure: \(\Theta\bigl(\delta \sum_i \log (n_i / \delta)\bigr)\) comparisons.
leapfrog
The cursor form of SvS used by PISA and Lucene: the rarest list proposes a candidate and every other cursor calls NextGEQ. A miss makes the larger docID the new candidate.
round-robin
Leapfrog Triejoin's unary case: cursors take turns seeking to the current maximum.
decode + SvS
Decode every list completely, then intersect the arrays (Lemire et al.).

Union

heap
k-way merge with a binary heap of cursors: \(O(N \log k)\).
min-scan
Scan all cursors for the minimum at every step (PISA's or_query): \(O(N k)\), but branch-friendly for small \(k\).
bitset window
Lucene's BooleanScorer: drain every cursor into a 4096-docID bitset, then scan the window's 64 words.
fold, bitmap
On uncompressed arrays: pairwise merges smallest first, or set bits in a bitmap spanning \([\min, \max]\) and scan it.

Experimental setup

The clustered collection mimics an index whose docIDs were reordered by URL or topic, the setting where modern indexes operate. The docID space is split into 1000 topic regions; each term draws 85% of its postings from a few preferred regions, in runs of about 4 consecutive documents, and the rest uniformly. The uniform collection uses the same list lengths with random docIDs, like an index in crawl order. WikiText-103 is real text: every paragraph of the training split is a document, in corpus order, so the paragraphs of one article are adjacent.

List lengths follow Zipf's law (\(n_r \approx n_1 / r\)). Queries take 2 to 4 terms that co-occur in a randomly sampled document, so conjunctions are rarely empty, as for real queries. Every measurement is the best of 3 timed passes over the whole query log, single-threaded, after a verified warm-up pass.

Results

Space against speed on a reordered index

On the clustered collection the 500 queries average 2.8 terms and touch 576,000 postings each; a conjunction returns 309 documents and a disjunction 563,000. The charts plot each codec's size on the query lists against its fastest algorithm; blue points are Pareto-optimal (nothing else is both smaller and faster).

  • The AND frontier has three members. It runs from interpolative coding (4.90 bits per posting, 0.14 ms) through PEF (4.94 bits, 0.035 ms) to Roaring (9.32 bits, 0.018 ms). PEF is within 1% of interpolative coding's size but 3.8× faster, because its NextGEQ is a select over the high bits instead of a block decode.
  • Roaring buys speed with space. It is 2.0× faster than PEF for AND and 5.8× faster for OR (0.38 against 2.21 ms), at 1.9× the size. Pibiri & Venturini report 4–8× (AND) and 14–18× (OR) for CRoaring over list codecs at about twice the space; the direction holds here, with smaller gaps on these skewed queries.
  • Block codecs sit in the middle. BP128 and the bitpacking crate take 0.051–0.065 ms at 7.69 bits, and OptPFor is about as fast at 5.92 bits, 23% smaller. VByte is 1.4× slower than BP128 with no space advantage. Uncompressed arrays (0.027 ms) beat every compressed list codec, PEF by 1.3×, at 6.5× its size.
  • Unions are bound by their output. Every list codec needs 1.8–3.5 ms, that is 3.2–6.2 ns per output docID, whatever its decoding speed. Only representations that OR whole machine words, or need no decoding, escape this: Roaring (0.38 ms, about 0.7 ns per result, or 0.23 ms if it only counts), the hybrid index (1.3 ms) and uncompressed arrays (1.32 ms with a pairwise merge, 1.73 ms through a bitmap).
  • Implementation matters as much as format. With identical containers and size, this crate's Roaring answers AND 3.0× faster than the roaring crate and OR 6.5× faster when docIDs are written out. When both only count, the OR gap shrinks to 2.7×, so most of the crate's union cost is its iterator. In the other direction, the bitpacking crate decodes BP128 blocks faster than my auto-vectorised unpacker (0.30 against 0.76 ns per posting).

Skipping beats decoding for conjunctions

The tables below give every algorithm's time on every codec (clustered collection; blue marks the fastest per row, not counting the count-only variants).

  • Rarest-first leapfrog is the best cursor conjunction for every codec. Driving the shortest list and calling NextGEQ on the others is 3.7–17× faster than decoding all lists and intersecting the arrays (43× for the roaring crate, whose decoding goes through a slow iterator). The gap is largest for the tries, PEF and Elias-Fano (15–17×), whose decoding is slowest relative to a jump.
  • Round-robin order costs 1.2–1.7×. Leapfrog Triejoin's round-robin seeks waste work when one list is much shorter than the rest, as here; it only won on two-term queries, and there by under 1%.
  • SIMD loses on real query shapes. On uncompressed arrays, SvS with galloping (0.029 ms) beats SvS with either NEON kernel by 7.7–9.5× (0.23–0.28 ms), although the 8×8 kernel wins by 6.8× on equal-size lists. The size ratios of real queries are large, so the adaptive kernel (0.027 ms, the fastest here) is the safe default. Small Adaptive (0.042 ms) and Sequential (0.052 ms) never beat SvS, which is Barbay et al.'s experimental finding.
  • Union algorithms: Lucene's bitset window or PISA's min-scan is the fastest cursor union for every codec, 1.2–1.6× faster than a heap of cursors. Native operations beat any cursor union for this crate's structures: 6.2× for Roaring and 2.4× for the hybrid index. The roaring crate's native union is 18% slower than a bitset window over its cursor.

What docID clustering buys

The uniform collection has exactly the same list lengths as the clustered one, but random docIDs. Comparing the two isolates the effect of docID order, which real systems control by reordering documents (by URL, or by recursive graph bisection).

  • Codecs that model local density gain the most. On the query lists, clustering cuts Run-Trie by 50%, Trie by 46%, interpolative by 42%, PEF by 39%, OptPFor by 33% and Roaring by 32%. BP128 gains 18% and VByte only 12%, because one wide gap still forces a wide block or extra bytes.
  • Plain Elias-Fano gains nothing (8.08 → 8.13 bits): its size depends only on \(u\) and \(n\), exactly as the formula says. On uniform data it ties PEF as the smallest codec, which is the case partitioning cannot improve.
  • Roaring and the tries pay most for randomness. At 13.2–13.7 bits per posting on uniform data they are 1.6–1.7× the size of PEF, because random docIDs leave few runs and many half-empty 16-bit arrays or trie paths.
  • Conjunctions get about 2× faster with clustering for every list codec (PEF 0.076 → 0.035 ms, BP128 0.145 → 0.065 ms), while Roaring changes little. Part of this comes from the workloads: the uniform queries touch 19% more postings and have smaller results, because random lists share fewer documents. The rest comes from skipping, since clustered lists put matching docIDs in fewer blocks and partitions.

Kernels: where merging stops paying

The pairwise kernels were timed on uncompressed random lists with a fixed short list of 10,000 docIDs and a long list 1 to 4,096 times larger. The chart plots nanoseconds per element of the short list, so a flat line means the cost tracks the short list (the \(m \log(n/m)\) regime) and a rising line means the long list is scanned (the \(m + n\) regime).

  • Similar sizes favour SIMD. At 1:1 the NEON 8×8 kernel takes 9.6 µs against 65 µs for the branchy merge, 6.8× faster. The NEON 4×4 kernel takes 24 µs, so even with 128-bit registers the 8-value block (two registers a side) is worth 2.5×. The branch-free merge (41 µs) beats the branchy one only at 1:1 and 1:2 and becomes the slowest kernel by 1:32, because its loop-carried dependency serialises every step.
  • Skew favours galloping. Galloping overtakes the 8×8 kernel between 1:32 and 1:64 and is 4.5× faster at 1:4,096 (4.5 ms against 19.9 ms). At 1:4,096 Baeza-Yates takes 1.3× galloping's time and plain binary search 3.6×; both lose badly when the sizes are similar (binary search needs 297 µs at 1:1).
  • The switch point is hardware-specific. The adaptive kernel uses CRoaring's 64× threshold. On the M2 that is too late: at 1:64 it pays 1.7× more than galloping (on the AVX-512 Xeon VM where this study first ran, galloping already won between 1:16 and 1:32). A threshold near 1:35 would track the lower envelope of both kernels, consistent with Baeza-Yates and Salinger's ~30:1 crossover for scalar code.

Longer queries

Each point uses 300 queries with exactly \(k\) co-occurring terms. As \(k\) grows from 2 to 6, the lists in a query hold more postings in total (400k to 740k–880k), yet every codec answers faster: the mean result shrinks from 744 to 2 documents, and the cost of a rarest-first conjunction follows the shortest list and the number of candidates it proposes, not the total length.

  • Roaring's lead narrows with more terms. It is 2.5× faster than PEF for two-term queries (0.019 against 0.046 ms) but only 1.6× faster at six (0.0069 against 0.011 ms). Selective conjunctions let cursor-based codecs take long NextGEQ jumps, while Roaring still visits every shared 2¹⁶ chunk, the effect Pibiri & Venturini describe.
  • Uncompressed arrays beat PEF at every length, by 1.3× at two terms and 2.2× at six, though they take more than six times the space.
  • Tries stay 2.8–3.3× behind PEF at every length. The likely reason is that the traversal pays a rank operation per trie level for every surviving region, which costs more than one cursor jump when a single list is very selective.

Real text: WikiText-103

WikiText-103 has 859,532 paragraphs, a 531,033-term vocabulary and 57 million postings. Its lists are far denser than the synthetic ones: function words occur in most paragraphs. The queries use terms with at least 100 postings and average 3.0 terms, with 64 documents per AND and 199,635 per OR.

  • Dense real lists suit Roaring. Its bitmap containers answer AND in 0.0043 ms, 3.8× faster than the fastest compressed list codec (PEF, 0.016 ms) and 2.1× faster than uncompressed arrays, and OR in 0.069 ms, 11× faster than any list codec with a cursor algorithm (0.75–1.3 ms) and 4.4× faster than the hybrid index. On the query lists it costs 8.47 bits per posting, 1.8× PEF.
  • The Elias-Fano family leads the list codecs: PEF and interpolative coding are the smallest (4.75 and 4.77 bits per posting on query lists), and Elias-Fano and PEF answer conjunctions 1.1–3.7× faster than the block codecs.
  • Small lists dominate whole-index space. Over all 531k lists the ranking changes: interpolative (8.46), Elias-Fano (8.51) and PEF (8.92) stay smallest, but the tries reach 23 bits per posting, because each of the many short lists pays for about 20 trie levels and their rank directories. Roaring pays a container header per list and lands at 15.4.
  • The OR algorithm matters as much as the codec. For every cursor codec, the Lucene-style bitset window is the fastest union, 1.4–2.0× faster than the heap.

Takeaways

  1. Choose the skip structure first, the gap coder second. Conjunctions spend their time in NextGEQ, so how a codec jumps matters more than how fast it decodes. Elias-Fano's select-based jumps made PEF the fastest compressed list codec for AND on every collection, although it decodes 1.3–1.5× slower than BP128. Uncompressed arrays, galloping through plain memory, are still 1.3–2.1× faster than PEF on the M2 (on the Xeon VM that first ran this study, PEF matched or beat them).
  2. PEF is the balanced default. It was the smallest or within 1% of the smallest codec on all three collections (4.75–8.08 bits per posting on query lists) and its AND time was 2.0–3.8× Roaring's. Interpolative coding matches its size but is 3.7–4.3× slower.
  3. Roaring is the speed choice, especially for unions. Container-wise operations with SIMD kernels gave the fastest AND on every collection and 4.8–11× faster OR than the best compressed list codec, because ORing words beats merging docIDs one at a time. The price is 1.6–1.9× PEF's space on query lists, and more on vocabularies with many short lists. Its AND advantage shrinks as queries get more selective (2.5× at two terms, 1.6× at six).
  4. Use SIMD only where sizes are similar. A NEON 8×8 block-compare kernel is 6.8× faster than a scalar merge on equal-size lists, but real conjunctions are skewed, and galloping wins beyond about a 1:35 size ratio on the M2. CRoaring's 64× switch point was measured on older hardware and should be re-tuned per machine.
  5. Reorder docIDs. Clustering cut the size of PEF, interpolative coding, Roaring and the tries by 32–50% and roughly halved conjunction time for list codecs. Plain Elias-Fano cannot benefit; partitioning is what lets it.
  6. Compact tries are compact, not fast, in this implementation. On clustered data they are smaller than BP128 and Roaring, but 2.8–3.3× slower than PEF for AND on every query length, and they pay heavily for short lists (23 bits per posting over the whole WikiText vocabulary). The paper measured lists of at least 4,096 postings on URL-sorted web collections; the queries here pair short lists with very long ones, where cursor skipping is hard to beat.
  7. Implementation quality changes the ranking. Two Roaring implementations with byte-identical containers differ by 3.0× on AND and 6.5× on OR. Published comparisons between formats should be read with that spread in mind.

Limits of these measurements. One MacBook Air with an Apple M2 (4 performance and 4 efficiency cores, 24 GB, macOS 26.0.1), on mains power, single-threaded, timed with the NEON kernels. Two independent runs of the same codecs agree to 0.3% at the median and within 3% in all but one cell (12%). The study first ran on a 4-core Emerald Rapids Xeon VM with AVX-512; the conclusions that changed on the M2 are noted above. Queries are generated from co-occurring terms rather than taken from a real query log. All operations are Boolean, with no scoring or top-k pruning, and every result is written out as a Vec<u32> unless marked "count only". Gov2 or ClueWeb in ds2i format, with real TREC queries, can be run with --source ds2i.

Reproduce

Everything is in Strata's postings module (strata/src/postings/) and the strata-posting-bench binary. The default build uses -C target-cpu=native; every SIMD path has a portable fallback.

cd strata
cargo test --release postings                      # every codec and algorithm
scripts/postings/prepare_wikitext.sh data          # optional: WikiText-103 (needs pyarrow)
scripts/postings/run_experiments.sh data/wikitext103.txt
python3 scripts/postings/build_report.py           # rebuilds this page from results/postings/*.json

# your own data: ds2i/PISA .docs collections or one document per line
target/release/strata-posting-bench run --source ds2i --input gov2.docs --queries q.txt --json out.json
target/release/strata-posting-bench run --source text --input docs.txt --codecs "pef,roaring,bp128"
target/release/strata-posting-bench kernels --small 10000 --ratios 1,4,16,64,256,1024
