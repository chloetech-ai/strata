posting_bench · new designs

Three new posting-list structures, one per region of the trade-off

The first round of experiments showed where existing structures leave room. Roaring is fast but large, PEF is compact but answers OR posting by posting, and nothing models the low entropy of reordered lists. I designed three new structures, each aimed at a different part of the size/speed frontier, built them in the same Rust testbed, and measured them on the same collections and query logs as the existing codecs.

8 of 10

On 8 of the 10 size/time frontiers (AND and OR on five workloads), every point is Pyramid, Loom or Entropic. Roaring keeps the fast end of AND on uniform and WikiText.

Where the room is

A new posting-bench stats command measures the structure of each collection over the lists its queries actually touch. Three facts shaped the designs.

  1. Postings are bimodal. On the clustered collection, 5.1% of the non-empty 256-docID blocks hold 32–255 postings and contain 69% of all postings. Two thirds of blocks hold exactly one, which is the topic-independent noise every term carries. WikiText is denser (12.4 postings per non-empty block on average), while uniform docIDs leave mostly singletons.
  2. Queries are skewed. The shortest list of a query has a median of 1,793 postings (288 on WikiText). The longest is a median 68–147× and a 90th percentile 965–2,705× larger. Conjunction cost is therefore set by probing a few thousand candidates against very long lists. Roaring spends about 10 ns per candidate.
  3. Entropy is left on the table. A per-list zero-order code of each gap's bit width (plus its raw low bits) would need 4.43, 7.41 and 3.95 bits per posting on the three collections. That is 8–17% below the best existing codec (PEF or interpolative coding), and context modelling can go lower still.

Entropic codes the gap structure with a context model.

Pyramid speed-first

Make every membership test O(1) at every density, and make every set operation local to a 256-docID block.

Roaring partitions the docID space into \(2^{16}\)-docID chunks and stores each as an array, a bitmap or runs. Its two costs on these workloads are the mid-density chunk and the skewed probe. A mid-density chunk is either a 16-bit-per-value array or an 8 KiB bitmap, with nothing in between. A probe into a large array chunk is a gallop. Pyramid adds one level and stores the two populations the statistics revealed separately: dense topical blocks and isolated noise.

Layout

Each chunk is split into 256 blocks of 256 docIDs and stored as one of three kinds, chosen by exact size:

  • Small: a sorted u16 array of at most 48 values, probed with masked AVX-512 compares.
  • Tiered: a 256-bit present mask, a 256-bit dense mask (omitted when no block is dense), one 256-bit bitmap per dense block, and the low bytes of the remaining values grouped by block.
  • Flat: the present mask plus all 256 block bitmaps, used for chunks that are dense almost everywhere.

A block becomes a bitmap when that is no larger than its sparse form: about 9 bits per value (8 for the low byte, about 1 for the directory), so

\[ \text{dense}(B) \iff 256 \le 9\,|B| \iff |B| \ge 29. \]

A Tiered chunk then takes

\[ S_{\text{tiered}} = 96 + 256 + 256\,[d \gt 0] + 256\,d + 8\,c_s + |\text{dir}| \ \text{bits} \]

for \(d\) dense blocks and \(c_s\) sparse values, where 96 bits are the chunk header and counts. Flat is taken whenever \(S_{\text{flat}} \lt 1.6\,S_{\text{tiered}}\). That bias toward bitmaps costs 0.07–0.23 bits per posting and made unions 14–17% faster in the profiling runs.

Directory for sparse blocks

The offset of sparse block \(b\) in the byte pool comes from one of two directories, chosen per chunk by exact size:

  • Unary ("byte Elias-Fano"): a bit vector \(U\) marks each block's first value, with a u16 sample every 8 blocks: \[ \mathrm{off}(b) = \mathrm{select}_1\bigl(U,\ \mathrm{rank}_{P \setminus D}(b)\bigr), \] answered by a single pdep over a 128-bit window. This wins for blocks of 1–3 values, the noise.
  • u16 prefix offsets: one load per lookup. This wins once sparse blocks average about 14 values.

Masks and directories sit in a sequential metadata arena read in key order and prefetched three chunks ahead; bitmaps and bytes sit in a 64-byte-aligned data arena.

Conjunction: driven chunks and block joins

// the rarest list's chunk keys are galloped in the others
for each chunk key shared by all lists:
    D ← the chunk with the fewest values
    if |D| ≤ 64 or (|D| ≤ 1024 and |D|/blocks(D) ≤ 8):    // driven chunk
        for each other list L, rarest first:
            keep the v ∈ D with probe_L(v)        // O(1), branch-free
    else:                                                // block join
        for each block b present in every list:   // AND of present masks
            if b is dense everywhere:
                emit the bits of ⋀ bitmaps_b      // 4-word AND
            else:
                test ≤ 32 low bytes at once against the others
                (vpermb bit lookups, byte compares);
                emit the survivors with vpcompressd

Cost is proportional to the smaller side of each chunk or block, and blocks absent from any list are never touched.

Union

Chunk groups that are dense (96 or more union blocks, or any Flat member) are accumulated in a thread-local 65,536-bit buffer that touches only present blocks. Sparse values are decoded 16 at a time: block ids come from a vpopcntd prefix count over \(U\), then vpermt2d. In sparse groups, runs of blocks owned by a single list are written straight to the output, and shared blocks go through a 256-bit accumulator. Bitmaps are extracted with vpcompressb, or with vpcompressd where VBMI2 is missing. The count-only union skips single-list runs entirely and adds their cardinalities.

Loom balanced

Keep PEF's size, but line dense partitions up on machine words and replace posting-by-posting cursor merging with partition-native algorithms.

PEF already chooses, per partition, whatever is smallest: a run, a bitvector or Elias-Fano. Its weakness is the query side. Every candidate costs a NextGEQ with a select, and a union merges cursors one posting at a time at 4.5–9 ns per output docID. Loom keeps the format and fixes both.

Layout

  • Word-aligned bitvectors. Bit \(i\) of a bitvector partition with base \(b\) is docID \(64\lfloor b/64\rfloor + i\). The bitvectors of any two lists then share the docID word grid, so they can be ANDed or ORed word by word without shifts. The padding of at most 63 bits is charged to the partition.
  • Finer partitions with a speed bias. The dynamic program runs on a 16-posting boundary grid (PEF uses 32) and divides bitvector cost by \(\lambda = 5/4\):
    \[ C(j) = \min_{\substack{i \lt j\\ j-i \le 4096}} \Bigl[ C(i) + 64 + \min\Bigl\{ \tfrac{1}{\lambda}\,\mathrm{BV}(i,j),\ \mathrm{EF}(i,j) + 12,\ \mathrm{RUN}(i,j) \Bigr\} \Bigr]. \]
    The finer grid saves about 1% and the bias spends it again on bitvectors, which probe in O(1) and OR word-wise, so total size stays at or just below PEF's. Each Elias-Fano partition carries 16-bit select samples every 256 zeros (PEF uses 32-bit samples) plus a 12-bit size field.

Conjunction

The shortest list is decoded in batches of 256 candidates, and each other list filters the batch in place, rarest first, stopping early once the batch is empty. How a list filters depends on its partition under the candidates:

  • Bitvector: a branch-free bit test. When the driver's own partition is also a bitvector, the two are ANDed word by word in bulk.
  • Run: a range check.
  • Elias-Fano, by the density ratio \(\rho\), the list's postings per candidate over the candidates' range:
\[ \text{mode}(\rho) = \begin{cases} \text{merge: decode the range, SIMD 16}{\times}16\text{ block intersection} & \rho \le 12 \\ \text{far probes: independent select per candidate} & \rho \ge 64 \\ \text{forward probes: 2–4 interleaved branch-free streams} & \text{otherwise.} \end{cases} \]

A far probe finds its bucket from the nearest select sample with an 8-word AVX-512 popcount prefix sum, without depending on the previous probe, so the CPU overlaps them. Forward probes return a lower bound, which lets the driver leapfrog over the list's gaps. When a batch empties, the driver jumps straight to the other list's next posting.

Union

Unions walk the docID space in windows of \(2^{16}\) docIDs (a 1024-word thread-local accumulator) and skip empty windows. Every list contributes the partitions overlapping the window: bitvectors are ORed word-wise, runs fill words, and Elias-Fano postings are decoded with SIMD (high bits through vpcompressd, low bits through vpermb and vpsrlvd) and set as bits. The window is then extracted with masked non-zero-word scanning and vpcompressd. Writing the output is about 60% of the remaining union time, at about 0.5 ns per docID.

Entropic space-first

Model the gap stream instead of bounding it: code each gap's class with an entropy coder conditioned on the recent past, and keep blocks skippable.

Gap codecs spend a whole number of bits per gap (VByte, BP128, OptPFor) or rely on a bound (Elias-Fano's \(2 + \lceil\log_2(u/n)\rceil\)). Interpolative coding adapts to runs but decodes slowly. In reordered lists the gaps follow a pattern: runs of 1s, bursts of small gaps inside a topic, then a jump to the next region. Entropic codes that pattern explicitly.

Symbols, contexts and cost

Each block of 128 postings codes its \(n-1\) gaps \(g_i = d_i - d_{i-1} - 1\). The last posting is the block maximum, which the skip table already stores. A gap becomes one of 64 tokens: gaps 0–3 are exact, and larger gaps are coded as their bit width \(w\) plus the bit below the leading one, leaving \(w-2\) raw bits. Token \(t_i\) is coded in the context of \(t_{i-2}\), so the size of a list is

\[ |\mathrm{enc}(\mathcal{L})| \;\approx\; \sum_i -\log_2 p_{c(t_{i-2})}(t_i) \;+\; \sum_i \max(0, w_i - 2) \;+\; |\text{model}| \;+\; |\text{skip}|, \]

which approaches the conditional entropy \(H(T \mid C)\) of the token stream. Contexts are 1–4 contiguous ranges of the token axis, chosen per list by dynamic programming over entropy plus model bits. Conditioning on \(t_{i-2}\) instead of \(t_{i-1}\) costs about 0.02 bits per posting, but it splits the stream into two independent chains that two tANS lanes decode in parallel.

Coder and models

  • Context-switching tANS. A decode step is one table lookup: the entry \((s, n_b, \beta)\) at the current state gives the token, the number of bits to read and the next state base, \(x \leftarrow \beta + \mathrm{bits}(n_b)\). Entries are 8 bytes and already point into the next context's table, so the critical path is one load, one bzhi and one or. State sizes of 7–10 bits are chosen per list.
  • Bits-back block starts. Each lane's final state also carries the low raw bits of that lane's last symbol, so the per-block initial states cost little.
  • Three model kinds, chosen per list by size (1–2 selector bits):
    • its own model, with 5-bit log-scale frequency levels;
    • a shared parametric model (zero-inflated geometric per context, a 20-bit index);
    • an "auto" model, geometric with the list's mean gap, at 0 bits.
    Models cost 0.002–0.018 bits per posting on the query lists.
  • Skip table. Elias-Fano sequences of block maxima and block bit offsets cost 0.17–0.21 bits per posting. A plain (u32, u32) entry per block would cost 0.5.

Queries

An AVX-512 gather decoder decodes eight blocks at once for bulk decoding. AND bulk-decodes the shortest list and filters it through lazy, block-caching cursors on the others, with early exit. OR sets bits in a bitmap over \([\min, \max]\) and extracts them with the shared SIMD extractor.

The price is build time, 13–19× PEF's because of model fitting, and decode tables built from the stored models when an index is loaded. They are not part of the serialized size, as with zstd's FSE tables, but they are reported below as auxiliary memory.

Evaluation

Same harness, same machine, same three collections and query generator as the first round. Every new structure passes the shared conformance tests, and every query result of every algorithm is verified against a reference before it is timed. Times are the best of three passes, single-threaded, with docIDs written out. Space is bits per posting over the lists the queries use. In the tables, index bits covers every list, aux MB is memory built at load time, and OR count is the fastest union that returns only the number of results.

Head to head

Each design was built to beat a specific reference: Pyramid against Roaring, Loom against PEF (and, as a stretch, Roaring), and Entropic against interpolative coding and PEF. The table gives each design's size and best AND and OR times relative to its reference. Green means smaller or faster.

  • Pyramid vs Roaring: 24–33% smaller on all three collections and 1.2–1.75× faster on unions. Conjunctions take 19% less time on clustered data, 11% more on uniform and 38% more on WikiText.
  • Loom vs PEF: the same size (0.4–0.9% smaller), 1.9–2.2× faster conjunctions and 4.9–8.9× faster unions. On clustered data Loom also beats Roaring on both operations at half its size.
  • Entropic vs interpolative coding: 11–14% smaller, 2.2–2.4× faster conjunctions and 3.5–3.9× faster unions. Against PEF it is 6–15% smaller with 2.2–2.7× faster unions, but conjunctions are about 2× slower.

Clustered collection

On the reordered-like collection the old codecs drop off both frontiers entirely. For AND the frontier is Entropic (4.22 bits, 0.089 ms) followed by Loom (4.90 bits, 0.021 ms). For OR it adds Pyramid (6.20 bits, 0.308 ms) at the fast end.

  • Loom answers conjunctions faster than Roaring (0.021 against 0.029 ms) and unions slightly faster (0.509 against 0.538 ms) at 53% of its size. That is the result the first round said was out of reach for a list codec.
  • Pyramid has the fastest union of any structure (0.308 ms, 1.75× Roaring), and 0.089 ms when only the count is needed (4.6× Roaring's count-only union).
  • Entropic is 14% smaller than interpolative coding (4.90 bits), the smallest existing codec, and still answers conjunctions 2.2× and unions 3.9× faster.

Uniform docIDs

With random docIDs there is no clustering to exploit, so the gains shrink but keep their direction. Entropic (7.60 bits) is 6% below PEF and Elias-Fano, the previous best. Loom answers conjunctions in 0.037 ms against PEF's 0.080, and unions in 0.74 against 3.63 ms. Pyramid is 24% smaller than Roaring and 1.3× faster on unions (0.366 against 0.480 ms). Roaring stays marginally ahead on conjunctions (0.034 against 0.037 ms for both Loom and Pyramid) and keeps the fast end of that frontier, at 1.7× Loom's size.

WikiText-103

On real text the lists are denser and queries more skewed (the shortest list has a median of 288 postings). Loom sits at PEF's size (4.74 bits) with 1.9× faster conjunctions and 8.9× faster unions (0.104 against 0.920 ms). Pyramid has the fastest union (0.068 ms) at 26% less space than Roaring. Roaring keeps the fastest conjunction at 0.007 ms against 0.010 ms for Loom and Pyramid.

Pyramid's remaining gap is the per-candidate cost of probing mid-density sparse blocks (about 12 postings per block here). Each probe reads a mask, a directory entry and a few bytes, while Roaring gallops through one contiguous u16 array. Entropic is again the smallest (4.18 bits, 12% below PEF).

Workload extremes

Two extra workloads on the clustered collection stress opposite ends:

  • Selective queries use only terms with at most 20,000 postings: 81 results per AND, 13,274 per OR. Loom has the fastest conjunction (0.007 ms against 0.010 for Roaring), and Pyramid the fastest union (0.059 ms against 0.100). Both frontiers again contain only Entropic, Loom and Pyramid.
  • Dense queries use only terms with at least 200,000 postings: 42,798 results per AND, 1.63 million per OR. Pyramid, Roaring and Loom tie on AND (0.766, 0.776 and 0.803 ms). On OR, Pyramid (0.674 ms) beats Roaring by 1.5× at 58% of its size on these lists, and Loom (1.24 ms) is 6.4× faster than PEF. Bitmaps win here, and both new structures store dense regions as word-aligned bitmaps.

Longer queries

Conjunctions mostly get cheaper as terms are added, because results shrink from 744 documents at two terms to 2 at six. Pyramid is the fastest at two to four terms (0.0187 ms at two, 1.4× Roaring). Loom takes over at five and six (0.0069 ms at six, 1.9× Roaring and 2.1× PEF), where each extra list empties its candidate batches sooner. Loom is 10% slower than Roaring at two terms and faster from three on. Entropic runs at 0.9–1.3× BP128's time at every length.

Memory and build time. Entropic's sizes are serialized sizes. When an index is loaded, it rebuilds decode tables from the stored models: 14.3 MB on clustered, 1.3 MB on uniform and 22.4 MB on WikiText. Held fully in memory, Entropic therefore takes about 27 MB on clustered against PEF's 18 MB, and 74 against 64 MB on WikiText. It only wins in memory if tables are built on demand for the lists a workload touches, which this implementation does not yet do. Building an index takes 2–10 s for Entropic, mostly model fitting, 0.3–1.5 s for Loom and Pyramid, and 0.1–0.8 s for PEF and Roaring.

Verdict

Each design met its main target and missed at least one secondary one. Together they hold every point on 8 of the 10 frontiers measured.

Pyramid: a smaller Roaring with faster unions

Met: 24–33% smaller than Roaring, the fastest union on every workload (1.2–1.75× Roaring), and faster conjunctions on clustered and selective queries.

Missed: conjunctions on uniform (11% more time) and WikiText (38% more). There, probes into mid-density sparse blocks cost more than Roaring's gallop through one contiguous array.

Loom: PEF's size with bitmap-like speed

Met: on every collection, PEF's size with 1.9–2.2× faster conjunctions and 4.9–8.9× faster unions. It sits on all ten frontiers and has the fastest conjunction for selective and five- or six-term queries.

Missed: the stretch goal of beating Roaring everywhere. On uniform and WikiText, Loom takes 9–37% more time than Roaring on AND and 25–54% more on OR. Roaring is 1.7–1.8× Loom's size.

Entropic: the smallest index on disk

Met: the smallest serialized index on every collection, 11–14% below interpolative coding and 6–15% below PEF, while answering queries 2–4× faster than interpolative coding.

Missed: it is not smaller in memory. Decode tables add 1.3–22 MB, which puts it above PEF on clustered and WikiText. Its conjunctions are about 2× slower than PEF's, and builds 13–19× slower.

Which one to use

  • Loom as the default. It replaces PEF outright, and takes at most 1.37× Roaring's conjunction time at 53–58% of its size.
  • Pyramid where unions dominate or memory is less tight, as in faceting, filters or OR-heavy candidate generation.
  • Entropic for cold or storage-bound tiers, where bytes on disk or over the network matter more than query time. It needs decode tables built on demand before it saves memory too.

Limitations

  • One machine. This is a shared cloud VM with an Emerald Rapids Xeon. Small timings vary by up to about 15% between runs, so differences under 10% (Loom against Roaring on uniform AND, the dense AND tie) are not significant.
  • AVX-512 kernels. Pyramid and Loom have scalar twins for every SIMD kernel, compiled when the target lacks the features, but only the AVX-512 builds were timed.
  • Tuned on these data. Thresholds such as 29 values per dense block, the 1.6× Flat bias and Loom's \(\lambda = 5/4\) were chosen while profiling these collections, so the margins may be smaller on others.
  • Boolean, static, single-threaded. No scoring, top-k or block-max metadata, no updates, one core. Queries come from the same generator as the first round rather than a real query log, also on WikiText.

Next steps

  • Pyramid: a contiguous u16 form for chunks made mostly of mid-density sparse blocks, so that a probe is one search instead of a mask, a directory entry and a byte scan. This targets the WikiText conjunction gap.
  • Loom: per-partition block-max scores for dynamic pruning. Its 16-posting grid already gives the boundaries.
  • Entropic: build decode tables lazily per list or share parametric models, so memory falls below PEF as well as disk.
