Engram: long-term context for a coding agent, in one Strata file

A coding session on a large project outlives its context window many times over. Engram stores everything Claude Code does through its hooks, finds what matters again with Strata's hybrid search, and decides on its own when to put it back into the prompt. The model can also search its history when it decides to. This page is the design, the implementation, and an evaluation on two long-conversation benchmarks, on the 26-hour session that built this repository, and in live Claude Code runs.

The problem

A context window is working memory. Long projects need a long-term memory that fills itself, and that is consulted only when it has something to say.

When a Claude Code session nears the end of its context window, it compacts: the history is replaced by a summary of about 15,000 characters. That keeps the plan and drops the particulars, such as the exact error, the number a decision rested on, or a preference stated once. A new session starts with only CLAUDE.md and an index of notes.

Reading more history is not the fix. On LongMemEval, GPT-4o answers 87% of questions when given only the relevant sessions, but 61% when given the whole 115,000-token history. A memory has to retrieve, and it has to retrieve selectively: in coding-agent experiments, an irrelevant memory lowered the solve rate below having no memory at all (26% with none, 22% with the wrong one).

So there are two decisions to make on every event, and the model should not have to make either one deliberately:

  • When to store: always, because storage is cheap and a missed record cannot be recovered. What varies is granularity and salience.
  • When to load: only when the evidence is strong, only within a small budget, and never for what is already in the window. The model can still pull more through tools when it knows it needs to.

Architecture

Strata takes an exclusive lock on its file, and hooks are short-lived processes that may run alongside the MCP server. So one daemon per project owns the store, and every hook and MCP call is a client on a Unix socket. The first client starts the daemon, which exits after 30 idle minutes. A client that cannot reach it in time prints nothing and exits 0, so memory never blocks a prompt or a tool.

Each record is one row of a Strata table: the text, an indexed context column, and fields for kind, session, sequence number, time, files and a 512-dimensional vector. The context column holds the request of the turn a tool result belongs to, or the section a summary chunk came from. A generated column indexes the text and its context together, so a tool output can be found by what the user was asking at the time. This follows LongMemEval's finding that expanding a record's index key works only when the expansion is indexed with the record.

When to store

Always, from the hook payloads. Nothing depends on the model deciding to save:

UserPromptSubmit

The prompt, plus a preference record for each sentence with a lasting rule ("always", "never", "from now on").

PostToolUse

The call and its result. Failures become error records. Long output is chunked and trimmed to its head and tail; Read results become stubs, since the file is on disk.

Stop

The final answer, the commentary written between tool calls (read from the transcript tail), and an episode card: prompt, files changed, commands, errors, outcome.

PostCompact

Claude Code's own summary, split by section. Pending tasks become todo records, and the live window restarts here.

Each kind carries a salience prior \(\iota\): preference 1.0, decision 0.9, summary and facts 0.8, prompts 0.7, errors and episodes 0.6, answers 0.5, tool calls and results 0.3. Replaying the 26-hour session through this capture gives 1,833 records up to the start of this task, and 2,204 for the whole transcript. The model can add durable knowledge itself with memory_remember, and mark older records as superseded.

When to load

Records still in the model's context are never injected. For session \(s\), the daemon keeps the window start \(w_s\): the sequence number at session start, or at the last compaction. Every recall excludes

\[ \{\, r : r.\mathrm{session} = s \,\wedge\, r.\mathrm{seq} \ge w_s \,\} \;\cup\; \mathrm{injected}_s . \]

There are three automatic load points and one pull path:

  • Session start, resume and compaction: a briefing of at most 2,500 characters. It covers stated preferences, recorded decisions, open tasks from the last summary, and where the previous session stopped. After a compaction it also recalls what is relevant to the last two prompts.
  • Every prompt: gated recall, described below.
  • Before Edit or Write: up to two earlier errors, decisions or episodes about that file, once per window.
  • Pull: the MCP tools memory_search, memory_timeline and memory_sql.

Ranking

BM25 over the text and its context, and cosine similarity over the vectors, each return their top 50 through Strata. Scores are min-max normalised over the union, with a missing score counting as 0. Priors break near-ties without overriding relevance:

\[ \mathrm{rel}(r) = w\,\widehat{\mathrm{bm25}}(r) + (1-w)\,\widehat{\cos}(r), \qquad S(r) = \mathrm{rel}(r)\bigl(1 + \lambda_\iota\,\iota(r)\bigr) + \lambda_t\, e^{-(\mathrm{seq}_{\max} - \mathrm{seq}(r))/\tau}, \]

with \(w = 0.5\), \(\lambda_\iota = 0.2\), \(\lambda_t = 0.05\) and \(\tau = 5{,}000\) records. Packing takes records by \(S\), at most two per turn so that more distinct evidence fits. Each record is cut to the 600 characters around the query's terms. The packed records are shown oldest first, each with its id, time, session, turn and kind, and labelled as possibly outdated. After them come up to five further candidates, one line each (id and opening words), which the model can open with memory_timeline.

Two kinds of record are never candidates:

  • Answers that admitted not knowing ("I don't know…"), which are stored with low importance and tagged.
  • Earlier copies of the question being asked.

Both match a repeated question best and carry nothing, so recalling them would only repeat the failure. The live tests below show why this matters.

The gate

Normalised scores cannot gate, because the best candidate always scores 1. The gate uses absolute evidence about the best candidates:

  • the highest cosine, and how far it stands above the tenth (\(\Delta_{\cos}\));
  • the highest IDF-weighted share of query terms a top-5 record contains;
  • how far the best BM25 score stands above the tenth (\(\Delta_{\mathrm{bm25}}\));
  • whether BM25 and vectors agree on the top record;
  • whether the prompt refers back ("earlier", "we decided", "did we").
\[ G = a\,\cos_{\max} + b\,\mathrm{cov}_{\max} + c\,\mathbb{1}_{\text{cue}} + d\,\mathbb{1}_{\text{agree}} + e\,\Delta_{\cos} + f\,\Delta_{\mathrm{bm25}}, \]
\[ \mathrm{cov}(q, r) = \frac{\sum_{t \in q \cap r} \mathrm{idf}(t)}{\sum_{t \in q} \mathrm{idf}(t)}, \qquad \Delta_{\cos} = \cos_1 - \cos_{10}, \qquad \Delta_{\mathrm{bm25}} = 1 - \frac{\mathrm{bm25}_{10}}{\mathrm{bm25}_1}. \]

A logistic fit on LongMemEval gives the weights and the two thresholds: \(\theta_{\text{hi}}\) holds precision 0.9 and \(\theta_{\text{lo}}\) precision 0.7. In the fit, positives are questions whose evidence the packed injection contains; negatives are questions asked against another conversation's store, abstentions and misses.

Evaluation

The evaluation has four parts:

  • Retrieval: two public long-conversation memory benchmarks, scored by whether the injected text contains the evidence.
  • This repository's session: 26 hours, two compactions, three projects, asked what it had lost.
  • Systems: latency and storage up to a million records.
  • Live runs: headless Claude Code sessions with Engram installed.

The default embedder is static (Model2Vec potion-retrieval-32M): a token lookup and a mean, 512 dimensions, about 10,000 records a second on four cores. BGE-small, a 33-million-parameter transformer, is the alternative; it took about 50 ms per short text on this CPU.
