Store everything as small records: a 400-byte window of one event is the value, the window plus its turn's request is the lexical key, and the window alone is the dense key. Keep every attribute a query can filter on. Derived records (episode cards, summaries, and model-written facts) are extra keys over the same history.

The queries

Every prompt (automatic)

First the knowledge query: the same two searches under kind IN ('preference','decision','fact','note','todo'), keeping at most 4 records not yet shown with cos ≥ 0.40 or coverage ≥ 0.30, whatever the gate says. Then lexical: bm25(body, :q) top 50, and dense: similarity(emb, :v) top 50, both under NOT (session = :s AND seq >= :w). Fuse, apply priors, gate, then pack at most 12 records, 8 per turn, within 4,000 characters (3 records within 1,200 on weak evidence).

Session start (automatic)

Structured only, newest first in each section: kind = 'todo' AND tag = 'planned', then 'preference', 'decision', 'fact', never superseded or done; the latest checkpoint's task list; the last session's episode cards. Within 6,000 characters, with a line telling the model to search memory before design decisions. After a compaction it also runs the prompt query on the last two prompts.

After each turn (background)

A small model reads the turn and the latest 40 knowledge records and writes new ones (tag = 'distilled' or 'planned'), retagging those it replaces 'superseded' and planned work it saw finished 'done'. Off the prompt's path.

Before an edit (automatic)

Structured and lexical: MATCH(files, :path) AND kind IN ('error','decision',…) ORDER BY seq DESC LIMIT 3, once per file per context window.

The model's own tools

memory_search (hybrid, with kinds), memory_timeline (session = :s AND seq BETWEEN :a AND :b), and memory_sql for any read-only question over the attributes.

-- "what failed in the planner yesterday?" through memory_sql
SELECT id, ts, text FROM memory
WHERE kind = 'error' AND MATCH(files, 'planner') AND ts >= 1791700000
ORDER BY ts DESC LIMIT 5

What to keep

Keep all of it. Raw events (prompts, answers, tool calls and results, the commentary between tool calls, compaction summaries) are the source of truth. Episode cards, summary sections and, next, model-written facts are keys derived from them, and can be rebuilt when the layout changes. Large tool outputs keep their head and tail, and file reads are stubs, since the file is on disk.

One trade-off left

On chat histories, 1,500-byte turns with no context gave the most correct answers (75.4%, against 73.0% for 400-byte windows; not significant). On coding sessions the windows win clearly. Engram is for coding sessions, so the windows stay. Cutting prompts and answers at 1,500 bytes and tool output at 400 is an untested middle path.

Done since: knowledge written by a model

The first item of the earlier list is in Engram now (see With and without Engram): at Stop, in the background, a small model writes decisions, rules, planned work and facts as their own records, with Engram's hooks off for that call. Strata needed no change for it. The knowledge query is a filtered hybrid search on kind, which Strata already plans as a scan of the few matching rows, and the briefing is a set of structured queries.

Next, in order of evidence

  1. Time-aware queries. Temporal questions are the second-largest gap (68–74% against 94% with the oracle). Phrases such as "yesterday", "last week" or "before the refactor" map to a ts or seq range that Strata already filters on.
  2. HTTP hooks. Claude Code can POST hook events to a URL for every event except SessionStart, which stays a command hook and starts the daemon. That removes a process start from each tool call (see Execution time). The daemon would need a secret path and a Host check, so that web pages cannot write into memory through localhost.
  3. A reranker on the top candidates of prompts that pass the gate, which still cannot tell related from relevant well.
  4. A larger briefing budget, or ranking within it. A long project will hold more knowledge than 6,000 characters. Beyond that, the briefing keeps the newest items and the knowledge query has to find the rest by similarity, which has not been tested here.
