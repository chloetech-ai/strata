What a memory record should be: keys, values and queries for Engram

Engram keeps a coding agent's running context in a Strata table and puts parts of it back into the prompt. Each stored record has a lexical key, a dense key, a value that gets injected, and attributes that queries filter on. This page compares ways to cut and key that context, on two long-conversation benchmarks, on the 26-hour session that built this repository, and by the answers a model gives from what is injected. It also covers where a prompt's time goes and what made it shorter. It ends with Claude Code itself, with and without Engram, on work that depends on earlier sessions. A first test found almost no difference; with the knowledge records added in response, Engram solved all 100 held-out runs against 60 without it. The structure that won is now Engram's.

A record, precisely

Retrieval for an agent's memory has three parts that are easy to conflate:

  • the key: what a query is matched against;
  • the value: what is put into the context when the key matches;
  • the attributes: what structured queries filter and sort on.

They need not coincide. A small key matches precisely but may not carry enough to answer. A context sentence added to a key helps a terse record be found, but can pull it ahead of the record that really holds the answer. A large value carries everything, but a fixed budget then holds only a few of them.

For a turn \(t\) cut into windows \(w_{t,1}, w_{t,2}, \dots\), record \(r_{t,k}\) has

\[ K_{\text{lex}}(r_{t,k}) = w_{t,k} \oplus \mathrm{req}(t)_{:200}, \qquad K_{\text{vec}}(r_{t,k}) = \phi(w_{t,k}), \qquad V(r_{t,k}) = w_{t,k}, \]

where \(\mathrm{req}(t)\) is the user request the turn answers and \(\phi\) the embedder. A prompt \(q\) becomes three queries over the same rows: its analysed terms for BM25 over \(K_{\text{lex}}\), its vector \(\phi(q)\) for approximate nearest neighbours over \(K_{\text{vec}}\), and a predicate \(P\) over the attributes that both searches apply. Engram's default predicate excludes what is still in the context window, \(P = \lnot(\text{session} = s \wedge \text{seq} \ge w_s)\). The two lists are fused, weighted by priors, and packed:

\[ S(r) = \bigl(w\,\widehat{\mathrm{bm25}}(q, K_{\text{lex}}(r)) + (1-w)\,\widehat{\cos}(\phi(q), K_{\text{vec}}(r))\bigr)\bigl(1 + \lambda_\iota\,\iota(r)\bigr) + \lambda_t\,e^{-\Delta\mathrm{seq}(r)/\tau}, \] \[ \text{pack: take records in order of } S \text{ while } \sum_{r \in P_B} \bigl(|V(r)| + h\bigr) \le B, \text{ at most } c \text{ per turn}, \]

with \(\widehat{\cdot}\) min-max normalised over the candidates, \(w = 0.5\), header cost \(h = 80\) characters and budget \(B\).

What was compared

A layout decides the keys: how a turn is cut into rows (whole turns up to 1,500 bytes, or windows of 800, 400 or 200 bytes on line, sentence or word boundaries), what context joins the lexical key (nothing, the request a response answers, or both sides of the exchange), and whether the vector embeds that context too. A presentation decides the value: the row itself or its best 600 bytes, the row widened inside its turn, the row plus the head of the other side of the exchange, or the whole turn.

Every combination is packed into budgets of 1,000 to 8,000 characters and scored on what reaches the model:

\[ \mathrm{AIC}@B = \Pr\bigl[\,a \sqsubseteq \mathrm{norm}(P_B)\,\bigr], \] \[ \mathrm{EIC}@B = \Pr\bigl[\,\exists\, e \in E : |P_B \cap e| \ge \min(80, |e|/2)\,\bigr], \] \[ \mathrm{All}@B = \Pr\bigl[\,\forall\, s \in S_E\ \exists\, e \in E_s : e \text{ shown}\,\bigr]. \]

AIC, the answer in context, asks whether the normalised answer string appears in the packed text. It only applies to questions whose answer appears word for word in an evidence turn and has at least four characters. EIC asks whether an evidence turn \(e \in E\) is shown. All asks whether every evidence session is shown, which matters for questions that aggregate over sessions. The data:

  • LongMemEval-S: 500 histories of about 115,000 tokens, one store each; 470 answerable questions, 147 with a verbatim answer.
  • LoCoMo: 10 conversations of about 600 short turns between two people; 1,536 questions.
  • This repository's session: 26 hours of Claude Code, replayed through Engram's capture into about 1,800 records. 67 probe questions are asked as if in a new session, and 32 after the second compaction (only about what the model no longer had). The answer counts when its regular expression matches the packed text.

Embeddings are static (Model2Vec potion-retrieval-32M, 512 dimensions), and every store is searched exactly so that the layout is the only variable.
