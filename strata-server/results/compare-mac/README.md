# Strata, Elasticsearch and Solr on a simulated cluster (Mac + kind)

**Mac + kind simulation, shared 4 CPUs.** Measured on 2026-10-28 with
[`deploy/compare/compare.sh`](../../deploy/compare/compare.sh) (method and
query mapping in [`deploy/compare/README.md`](../../deploy/compare/README.md)).
Every Kubernetes node is a container in one Docker VM on one laptop, so the
three engines, the client and Kubernetes share the same 4 CPUs; numbers
compare the engines with each other on equal terms, not what any of them
does on real machines.

| | |
|---|---|
| machine | MacBook Air, Apple M2 (4 performance + 4 efficiency cores), 24 GB, macOS 26.0.1 |
| Docker | Docker Desktop, engine 24.0.5, VM with 4 CPUs and 8.7 GB, LinuxKit kernel 5.15.49 |
| Kubernetes | kind 0.33, Kubernetes 1.37.0: 1 control plane and 3 workers |
| engines | Strata at `main` 6b85211 plus this branch (image `strata-server:compare`); Elasticsearch 9.5.5 (Basic licence, its default); Solr 10.1.0 (Lucene 10.4) |
| data | BEIR Quora: 522,931 questions, Cohere embed-english-v3 vectors (1,024 dimensions), synthetic `year`, `category`, `rating` |
| shards | 2 per engine, no replicas, one on each of two workers; clients on the third worker |
| budget | 3 CPUs and 6 GiB per engine (Kubernetes limits): Elasticsearch and Solr 2 data nodes of 1.5 CPUs and 3 GiB; Strata 2 shards and a coordinator, split two ways (below) |
| queries | the 9 kinds of `strata-server-bench`, 300 Quora queries, 6 s per kind at 1, 4 and 16 clients, round-robin over the engine's nodes |
| runs | one engine at a time; Mac load average 3 to 5 before each step |

Files: `tables.md` (every table, generated by
[`deploy/compare/analyze.py`](../../deploy/compare/analyze.py)),
`latency-full.md` (q/s, p50, p90, p95, p99, p99.9, max and mean for every
engine, kind and client count), `run-*.json.gz` (timings and every answer),
`load-*.json`, `build-strata-s*.json`, `cpu*.jsonl` (each pod's cgroup CPU
time around each step), `summary.json` (scores), and `first-pass/` (the
first run of every engine, before the fixes listed at the end).

## Summary

- **Latency, one client:** Strata's median is 0.3 to 1.8 ms across the nine
  kinds, Elasticsearch's 0.65 to 3.2 ms, Solr's 0.8 to 4.9 ms. BM25 is 4.7
  times faster than Elasticsearch (0.68 against 3.20 ms) and vector search
  3.6 times (0.58 against 2.12 ms), with p99 under 3 ms for every Strata kind.
- **Throughput, 16 clients:** Strata leads on BM25 (2.6 times Elasticsearch,
  2.7 times Solr), vector (2.7 and 5.8 times), vector + filter (1.8 and 7.4
  times), key lookups (1.4 and 3.4 times) and the boosted kind (1.4 times
  both). Elasticsearch ties it on facets (6,272 against 6,158 q/s), and
  Strata and Solr are close on BM25 + filter (2,003 against 1,886).
- **Answers:** the same quality where the kinds mean the same thing: BM25
  nDCG@10 0.790 (Strata), 0.788 (Elasticsearch), 0.793 (Solr); vector
  recall@10 against an exact search 0.986, 0.984 and 0.993 (Solr keeps only
  full-precision vectors); with the `rating` filter 0.991, **0.934** and
  0.998. Strata's normalised weighted hybrid scores nDCG 0.905 against 0.827
  and 0.823 for the raw-score sums the other two can do.
- **Load:** Strata built both shards in 225 s (one after the other, from the
  source files), Elasticsearch took 521 s (bulk + force merge to one
  segment), Solr 1,083 s (its optimize alone 572 to 597 s). Index sizes: 2.82,
  2.78 and 2.24 GB (Strata and Elasticsearch keep full vectors and 8-bit
  codes; Solr full vectors only).
- **Missing kinds:** Elasticsearch's free licence refuses RRF (`current
  license is non-compliant for [Reciprocal Rank Fusion (RRF)]`) and has no
  normalised linear fusion either; Solr has neither normalised fusion. Both
  are flagged below, not substituted silently.

At 16 clients every engine's p99 is inflated by CPU quota throttling (a pod

cgroups show each Elasticsearch and Solr node throttled for 12 to 20 s of

client shares the same 4 CPUs.

### How Strata splits its 3 CPUs

Elasticsearch and Solr nodes both hold data and coordinate; Strata's
coordinator is a pod of its own, so its budget has to be split. The first
split (shards 1.25 CPUs each, coordinator 0.5) throttled the coordinator in

each, the shards are the ones throttled.

## Answers

nDCG@10 is against Quora's relevance judgments for the same 300 queries;
recall@10 is against an exact dot-product search over all 522,931
documents (with `rating >= 4` for the filtered kind). The filtered and
boosted kinds rank by something other than relevance, so their nDCG is low
for every engine and only comparable across engines.

- **BM25** differs in two ways, both visible in the overlap: Strata sums
  term statistics over the shards (an extra round), while Elasticsearch and
  Solr score each shard with its own statistics by default; and Strata counts
  a query term once even when it repeats, while they count a repeated one
  (`pencils ... pencil`) twice. Over queries without a repeated term the overlap is 0.92, with one
  0.78. Ranking quality is the same.
- **Facets:** Strata's counts are exact. Elasticsearch's `terms`
  aggregation matched all 300. Solr's JSON facets over two shards missed the
  true 5th category in 9 of 300 queries even with `refine: true` (each shard
  proposes only a few more than the 5 asked for), and without refinement (the
  default) gave different counts in 37 of 300.

## What each engine's kind does differently

- **Hybrid (RRF):** Elasticsearch needs a paid licence (refused, so no
  numbers). Solr 10's combined-query handler fuses the knn top 100 with the
  lexical results up to the request's `limit` (its documentation shows no
  separate depth), where Strata fuses each input's top 100.
- **Hybrid (weighted):** Strata min-max normalises each input over the union
  of their top 100 and sums `0.2 · bm25 + 0.8 · similarity`. Elasticsearch
  (free licence) and Solr can only add raw scores: the lexical matches (all
  of them) plus the knn top 100, boosted 0.2 and 0.8 (Solr's BM25 boost 0.44,
  since it leaves out the factor k1 + 1 = 2.2 that Strata and Elasticsearch
  keep). That is less accurate (nDCG 0.83 against 0.905) and, for
  Elasticsearch and Solr, more work.
- **Boosted (bm25 × decay):** Strata multiplies the scores of its top 100
  BM25 matches (its fusion depth); Elasticsearch's `function_score` and
  Solr's `{!boost}` score every match. So Strata does less work for this
  kind and its top 10 differs (0.65 overlap; Elasticsearch and Solr agree
  with each other at 0.97). The equivalent there would be a rescore of the
  top 100, not measured here.
- **Vectors:** Strata and Elasticsearch search 8-bit codes (HNSW, ef 64) and
  re-score the best 40 with full vectors; Solr has no such re-scoring, so it
  searches full-precision vectors (topK 64), which costs it latency under
  load (four times the bytes per vector to read).

## Run to run

Each engine was timed twice (`first-pass/` holds the first). Between the
two, throughput per kind moved by up to 22% (Elasticsearch, Strata at 1 +
1 + 1: -19% to +15%), and a throttled coordinator varies more (Strata's
weighted hybrid at 0.5 CPU, one client: 238, then 547 q/s). Differences
under about 20% between engines are within that noise; the ones in the
summary are larger.

## Fixed or noted on the way

- Strata's shard builds first ran side by side in 3 GiB each and were
  killed for lack of memory (a shard's bulk build holds its documents in
  memory); they now run one after the other with the engine's whole budget.
- The facet word: Strata's `MATCH` analyses it as documents are, keeping
  query stopwords; the first pass of Elasticsearch and Solr dropped it as a
  query stopword (4 queries with no answer). Both now look up the analysed
  term.
- Solr's first load reported 522,879 documents (core status) of 522,931
  sent, with no error; the second load had all 522,931 searchable, and the
  first index was gone before the cause could be found. Solr's scores above
  are from the second load.
- Elasticsearch's second load took 549 s against 521 s for the first,
  while an image was being built on the same VM; the summary quotes the
  first.

## What to do next

- Try a Strata split between the two measured (for example 1.15 + 1.15 +
  0.7), or run the coordinator on the shards' nodes.
- Give Elasticsearch and Solr the same boosted semantics (a rescore of the
  top 100) and time that.
- Repeat on separate machines, where each shard has its own CPUs and the
  client none of theirs.
